## 1. 结论

PuddingClaw 的知识库系统不应该被定义成单一 RAG 系统，而应该被定义成：

> 用户本地知识与数据资产工作台。

一个入口接收异构资料，后端根据资料类型分流到最合适的处理引擎：

| 资料类型 | 主要目标 | 主处理引擎 | 主查询工具 |
| --- | --- | --- | --- |
| PDF / Markdown / 图文资料 | 长文档理解、引用、图文召回 | MinerU + LlamaIndex | `llamaindex_knowledge_query` |
| Excel / CSV / TSV | 单表或少量表的统计、筛选、排序、聚合 | PandasQueryEngine | `pandas_knowledge_query` |
| 结构化数据库 | 多表 SQL、业务数据分析、大数据量查询 | Vanna + SQL Engine | `database_knowledge_query` |
| 本地 Markdown 原文 | 精确文件定位、全文 grep | glob / grep | DeepAgents 文件工具 |
| 后期 LLM Wiki / gbrain | 概念、实体、关系、知识组织 | gbrain / LLM Wiki | 待定 |

第一性原理：

1. 文件是资产，不等于索引。
2. PostgreSQL 是账本和结构化事实库，不是 PDF/图片的存放地。
3. Milvus 是本项目高级版本的主向量索引；pgvector 只作为 PostgreSQL 内部的轻量可选增强，不是主线。
4. Pandas 负责小中型表格计算，Vanna 负责数据库 SQL 生成。
5. 用户只有一个上传入口，系统内部自己判断格式和 pipeline。
6. PuddingClaw 的目标是 AI Native BI：BI 的资产和术语要保留，但实现方式优先使用自然语言 reference，而不是先做传统强关系建模。
7. 数据语义层是“数据版 Skill reference”：Agent 在查数据前，应先读数据模型 reference / 度量值 reference / 资产 profile，再选择工具。
8. Agent 工具边界必须清晰，避免模型“太勤快”混用 grep、RAG、SQL。


### 3.1 文件系统

用户知识库目录保存真实文件：

```text
knowledge/
  originals/
    20260705/
      xxx.pdf
      xxx.xlsx
  imported/
    20260705/
      xxx.md
      xxx.csv
      xxx.xlsx
  assets/
    20260705/
      ...
  .puddingclaw/
    table_profiles/
      tbl_xxx.profile.json
  references/
    sales_semantic.md
    finance_metrics.md
```

规则：

- PDF：保存原始 PDF，MinerU 产物进入 Markdown + assets。
- Markdown：直接保存到 imported。
- Excel / CSV：上传入口仍走知识库统一导入；文件先落盘，再由“智能问数”工作台识别为 table asset，生成 table profile / sheet metadata；不默认转 Markdown。
- 聊天附件：先进入 session attachment，必要时注册为临时资产；用户选择保存后进入正式 knowledge。

### 3.1.1 数据语义层文件

语义层不要只放在数据库里，也要在用户知识库目录里有可读、可审计的 reference 文档。它的作用类似 skills 里的 `SKILL.md` / `references/`：

| 类型 | 作用 |
| --- | --- |
| Skill reference | 告诉 Agent 某个工具、领域或工作流应该怎么用 |
| 数据语义层 reference | 告诉 Agent 某批数据应该怎么理解、怎么查、怎么算 |

因此，PuddingClaw 的数据资产不只是一个文件，还应该有伴随的 profile。reference 分两层：资产级 reference 说明表自身；模型/指标/分析包 reference 说明业务口径。

```text
knowledge/
  imported/
    20260706/
      销售明细.xlsx
      预算表.csv
      行业白皮书.md
  .puddingclaw/
    table_profiles/
      tbl_sales.profile.json
      tbl_budget.profile.json
  references/
    sales_semantic.md
    finance_metrics.md
```

示例：

```md
# 销售数据说明

## 表：销售明细
一行代表一笔订单。

## 常用指标
- 销售额 = SUM(金额)
- 订单数 = COUNT(DISTINCT 订单号)
- 客单价 = 销售额 / 订单数

## 字段别名
- 收入、GMV、销售额 -> 金额
- 地区、区域、大区 -> region
- 商品、产品 -> product_name

## 注意
退款订单需要排除 status = "refunded"。
```

这层是后续 Pandas / Vanna / LlamaIndex 之间保持一致口径的关键。

### 3.2 PostgreSQL

PostgreSQL 不存实际文件本体，主要存管理记录：

- knowledge document catalog
- document revision
- import job / vector publish job
- artifact path / virtual path
- table profile
- semantic profile / reference path
- database connection metadata
- Vanna training job
- query history / generated SQL / execution result summary

### 3.3 AI Native BI 语义层架构

语义层是所有数据类工具的共同前置层。这里的目标不是复刻传统 BI 的重型建模器，而是做一个 AI Native BI：

> 让 Agent 像阅读 Skill reference 一样阅读数据模型、度量值和业务口径，然后再调用 Pandas / SQL / Vanna 工具。

这意味着：

- 数据模型 reference、度量值 reference 都优先是 Markdown / 自然语言文本。
- 度量值、维度都可以采用 Skill-like Markdown 资产，文件 metadata 只作为机器索引，正文才是业务语义。
- 度量值是顶层 BI 资产，可以被多个数据模型复用。
- 结构化关系、主外键、字段映射只在必要时补充，不作为第一阶段的默认复杂度。
- 产品术语向 BI 靠齐：数据资产、数据模型、度量值、维度、问数 Agent。

语义层解决的不是“怎么存文件”，而是：

- 这份数据代表什么业务对象。
- 每一行是什么粒度。
- 哪些列是时间、金额、实体、状态。
- 常用指标怎么计算。
- 用户会用哪些自然语言别名。
- 多个表之间能不能关联，应该按什么字段关联。
- 哪些字段有权限或安全限制。

在产品形态上，这层不要把所有东西都揉成一个概念。建议拆成三层：

```text
数据模型 = 一组可用于问数的数据资产 + 模型 reference
度量值 = 顶层可复用的业务指标/算法 reference
分析模型包 = 数据模型 + 推荐维度 + 推荐度量值 + reference，开箱即用
```

也就是说，用户可以先配置一个“数据模型”，表示“我要分析哪些数据，以及这组数据该怎么理解”；再选择“配置率、快充倍率、销售额”这类顶层度量值；最后系统可以把常用组合打包成“分析模型包”，让用户开箱即用。

总体结构：

```text
用户问题
  -> 选择/匹配分析模型包或数据模型
  -> 资产检索 / 数据源选择
  -> 读取 profile.json
  -> 读取 semantic reference
  -> 读取可用维度 / 可用度量值 / relationships
  -> 判断工具
       文档/图片 -> llamaindex_knowledge_query
       表格计算 -> pandas_knowledge_query
       正式数据库 -> database_knowledge_query
  -> 执行工具
  -> 返回答案 + 来源 + 使用的数据口径
```

语义层包含两类文件：

| 文件 | 面向对象 | 内容 |
| --- | --- | --- |
| `*.profile.json` | 机器 | 文件名、sheet、列名、类型、样例值、行数、候选 join key、资产 ID |
| `references/assets/*.md` | Agent / 开发者 / 高级用户 | 单个表格资产自身说明：一行代表什么、字段别名、注意事项 |
| `models/*.model.json` | 机器 + 前端 | 数据模型索引，主要保存名称、资产列表、reference 路径、权限、默认工具；不强制建传统关系 |
| `models/*.model.md` | Agent / 高级用户 | 数据模型 reference，像 Skill reference 一样说明这组数据怎么理解、怎么问 |
| `semantic-assets/measures/**/measure.md` | Agent / 高级用户 + 前端索引 | 顶层度量值 reference。metadata 至少包含 `name` 和 `type=measure` 供前端展示；正文包含自然语言口径、公式提示、适用模型/资产、禁止字段、查询步骤；可被多个模型复用 |
| `semantic-assets/measures/**/references/*.md` | Agent / 高级用户 | 度量值专用口径 reference。只描述特定业务对象的识别规则，例如空气悬架从 `type_name='可调悬架种类'` 且 `type_value` 包含 `空气悬架` 判断；不重复维护上市时间、价格段等维度口径 |
| `semantic-assets/grains/**/grain.md` | Agent / 高级用户 + 前端索引 | 颗粒度 reference，定义度量值按什么统计对象计算，例如款型颗粒度、车系颗粒度。metadata 至少包含 `name` 和 `type=grain`；正文描述分子/分母去重对象、归属传播规则和适用场景 |
| `semantic-assets/dimensions/**/dimension.md` | Agent / 高级用户 + 前端索引 | 维度 reference，产品上归入“语义资产”分类。metadata 至少包含 `name` 和 `type=dimension` 供前端展示；正文描述字段口径、派生规则和禁止推断规则 |
| `packages/*.package.json` | 机器 + 前端 | 开箱分析模型包，引用数据模型、推荐维度、推荐度量值和 reference |
| `packages/*.package.md` | Agent / 高级用户 | 分析模型包说明，像 Skill reference 一样指导 Agent 如何问数 |

语义资产 metadata 边界：

```markdown
---
formatter: semantic-asset
name: 配置率
type: measure
---

配置率 = 搭载某配置的对象数量 / 对象总数量。
```

```markdown
---
formatter: semantic-asset
name: 上市时间
type: dimension
---

上市时间取 `vehicle_params` 中 `type_name='上市时间'` 的 `type_value`。
禁止从 `car_name` 中的 25款/26款推断上市年份。
```

- 后端第一版必须解析 `name` 和 `type`，用于前端列表、卡片、筛选和选择。
- `formatter`、`description`、`tags`、`aliases` 等字段可选，解析后透传即可。
- 前端信息架构上，`type=measure` 和 `type=dimension` 都归入“语义资产”分类，不单独新增左侧“维度”入口。
- 计算口径、字段解释、禁止规则和多步查询策略留在 Markdown 正文中，运行时由问数 Agent 读取。
- 前端不需要理解正文，也不负责把正文编译成 SQL。

Agent 的行为约束：

1. 查询 Excel / CSV / 数据库前，优先匹配用户选择的分析模型包或数据模型。
2. 如果用户没有显式选择，则按问题、资产、数据源、维度/度量别名自动匹配。
3. 读取数据模型中的数据资产、模型 reference、权限规则；如果存在结构关系，再作为辅助约束读取。
4. 按用户选择或问题意图读取相关度量值和维度 reference。不能只根据 metadata 的 `name/type` 推断计算口径。
5. 如果选择的是分析模型包，再读取 package 中预置的推荐维度、推荐度量值和业务说明。
6. 再通过 catalog 找到相关 asset，并读取 asset profile。
7. 如果存在 semantic reference / package reference，像读 Skill reference 一样读它。
8. 再决定调用 PandasQueryEngine、Vanna 或其他数据工具。
9. 工具输出要带上使用的数据模型、度量值、维度、profile/reference，方便前端引用和调试。

这能避免模型直接看到一堆列名就猜 SQL 或 pandas 逻辑。

### 3.3.0 语义资产运行时方案

度量值和维度是 AI BI 的语义资产，不是传统 BI 的固定维表/指标表。第一版实现应优先支持用户用 Markdown 写清业务口径，再由后端按需喂给 Agent。

#### 目录与文件

语义资产统一放在：

```text
backend/semantic-assets/
```

文件形态：

```text
backend/semantic-assets/measures/**/measure.md
backend/semantic-assets/measures/**/references/*.md
backend/semantic-assets/grains/**/grain.md
backend/semantic-assets/dimensions/**/dimension.md
```

产品上两者都归入“语义资产”分类；`type=dimension` 不单独成为左侧一级入口。

#### 文件系统能力

`/semantic-assets/` 要和 `/skills/` 一样成为后端可读写路径：

- DeepAgents `FilesystemBackend` 挂载 `/semantic-assets/`。
- terminal path aliases 支持 `/semantic-assets`。
- `/api/files` 允许 `semantic-assets/`。
- `write_file` 允许 `semantic-assets/`。

#### 新建与导入

语义资产管理应复用 Skills 的使用方式：

- 新建语义资产时生成带 YAML frontmatter 的 Markdown 模板。
- 用户选择 `measure` 时写入 `semantic-assets/measures/{slug}/measure.md`。
- 用户选择 `grain` 时写入 `semantic-assets/grains/{slug}/grain.md`。
- 用户选择 `dimension` 时写入 `semantic-assets/dimensions/{slug}/dimension.md`。
- 支持 ZIP 导入。
- 支持文件夹导入，前端使用 `webkitdirectory`，后端按相对路径还原。
- ZIP / 文件夹至少需要包含一个 `measure.md`、`grain.md` 或 `dimension.md`。
- 导入完成后刷新 semantic asset registry。

#### Registry / Cache

不要每次问数都扫描文件系统。参考 SkillsMiddleware 的模式：

```text
后端启动 / 手动刷新 / 保存语义资产
  -> 扫描 backend/semantic-assets
  -> 解析 measure.md / dimension.md frontmatter
  -> 解析 grain.md frontmatter
  -> 建立应用级 index cache

database_knowledge_query 调用时
  -> 从 registry 读取 index
  -> 根据用户问题匹配候选资产
  -> 命中 measure 后继续匹配该 measure 目录下 references/*.md
  -> 只读取命中的 Markdown 正文
  -> 注入 Vanna prompt / Trace
```

Registry 是应用级资源，不放入每个 session state。每轮只把命中的语义资产片段放入当前问数上下文。

#### `database_knowledge_query` 集成

对 Agent 暴露层第一版不新增 `semantic_asset_search` 工具。语义资产解析是 `database_knowledge_query` 的内部强前置：

```text
database_knowledge_query
  -> semantic_asset_resolver
  -> table_router
  -> Vanna references/entities
  -> Vanna SQL generation
  -> read-only SQL runner
```

这样可以避免 Agent 忘记先查语义资产，也减少多工具链路不稳定。

#### Prompt 注入

不把所有语义资产放进 system prompt。system prompt 只放稳定规则：

```text
查询前必须优先使用已注入的语义资产定义。
度量值和维度定义高于字段名猜测。
如果语义资产声明禁止某种推断，不得使用该推断。
```

命中的 `measure.md` / `dimension.md` 正文按需注入本轮 Vanna question/context，作为强约束。

#### Trace

Trace 需要新增 `database.semantic_assets` 阶段，展示：

- 命中的资产名称。
- `type=measure` / `type=dimension`。
- 文件路径。
- 命中原因。
- 未命中的关键业务词。

这用于区分“语义资产没命中”“命中了但 Vanna 没遵守”“SQL 本身执行慢”。

#### 当前实现状态

截至 2026-07-08，第一版语义资产链路已落地：

- 后端启动、手动刷新、创建、导入、文件保存后刷新 `analytics.semantic_assets` registry。
- 智能问数页面“语义资产”支持列表、刷新、新建 YAML 模板、ZIP/文件夹导入。
- `database_knowledge_query` 内部调用 `semantic_asset_resolver`，按 `name`、`aliases`、`tags`、正文关键词和中文短语匹配语义资产。
- 命中的 `measure.md` / `dimension.md` 正文已注入 Vanna SQL 生成上下文。
- Trace 已新增 `database.semantic_assets`，前端显示命中数量、可用数量和是否注入。
- 内置基础语义资产：`上市时间` 维度、`配置率` 度量值、`款型颗粒度`、`车系颗粒度` 和 `空气悬架配置率口径` reference，用于约束 `vehicle_params` 的上市时间、配置率、统计对象和特定配置识别规则。

#### 数据库优化边界

当前阶段先不要求改数据库表结构。语义资产的目标是让数据分析师可以用自然语言定义口径；索引、物化视图、车型级事实表是后续性能优化，不作为第一版前置条件。

后续如需优化：

- 对上市时间、品牌、车系、价格段这类高频维度做结构化/索引。
- 对配置项采用通用访问索引，例如 `(type_name, car_name)`，不为 400 多个配置逐一建索引。
- 高频分析再考虑车型级缓存表或物化视图。

### 3.3.1 问数 Agent 运行模型

问数 Agent 不应该只是一个普通工具函数，而应该是一个可以独立运行、也可以被主 Agent 派发的预编译 Agent。

核心结论：

```text
data_analyst = 预编译 Agent 类型
  固定：
    - 角色：AI Native BI 问数 Agent
    - 工具边界：Pandas / SQL / Vanna / profile/reference 读取
    - 安全策略：不乱读文件、不乱用 Web、不绕过 catalog
    - 执行流程：先读模型/度量值/profile，再执行计算
    - 输出格式：答案 + 来源 + 度量值口径 + 维度/过滤条件 + 结果表/图表 artifact

运行上下文 = 每次运行时解析出来的可选约束
  来源：
    - 智能问数页面当前选择
    - 普通 Agent 派发时的会话线索
    - 当前 analytics session 历史
    - catalog 自动发现结果
```

也就是说，问数 Agent 的“能力定义”是固定的，但“本轮用哪个数据模型、哪些度量值、哪些数据资产”来自运行上下文。运行上下文不是裸 JSON 丢给 LLM，而是先被后端解析，再拼成稳定的 prompt context。

#### 独立 session

只要问数 Agent 能独立运行，它就必须有自己的对话历史和 session 管理。问数是连续分析，不是单轮函数调用。

示例：

```text
用户：统计第 45 周比亚迪销量
Agent：第 45 周销量是 ...

用户：那环比呢？
Agent：这里的“那”沿用上一轮的第 45 周和相同数据源，计算相对第 44 周变化。

用户：按车系拆一下
Agent：沿用上一轮数据源和时间范围，按车系维度 group by。
```

因此需要独立的 Analytics Session：

```text
analytics_sessions
  id
  title
  workspace_id
  linked_chat_session_id nullable
  current_selection_json
  context_snapshot_json
  created_at
  updated_at

analytics_messages
  id
  analytics_session_id
  role
  content
  metadata_json
  created_at

analytics_runs
  id
  analytics_session_id
  question
  status
  selected_context_json
  tool_calls_json
  result_json
  artifacts_json
  created_at
```

普通 Agent 和问数 Agent 的关系：

```text
普通 Agent Session
  -> 发现用户问题是问数任务
  -> 创建或复用 analytics_session
  -> 把问题和少量线索交给 data_analyst
  -> 回填答案到普通聊天
  -> analytics_session 保留完整问数历史、工具调用和结果 artifact

智能问数页面
  -> 直接操作 analytics_session
  -> 用户选择数据模型/度量值/资产
  -> 直接运行 data_analyst
```

两边可以关联，但不要混用一份消息历史。普通聊天历史面向通用助手；Analytics Session 面向连续数据分析。

#### Prompt Context Builder

API 请求中的 `workspace_id`、`session_id`、`selection` 不能只存在于后端参数里；LLM 必须通过 system/developer context 知道本轮约束。但也不能把原始 JSON 直接塞进 prompt。

需要一个 `AnalyticsPromptContextBuilder`：

```text
AnalyticsPromptContextBuilder
  -> load analytics_session
  -> load recent analytics_messages
  -> resolve current_selection
  -> resolve selected / candidate data assets
  -> load data model reference
  -> load measure references
  -> summarize table profiles
  -> render system context blocks
  -> return prompt_context + trace_payload
```

最终给 `data_analyst` 的结构应该是：

```text
Base System Prompt
  固定说明 data_analyst 是 AI Native BI Agent。

Analytics Runtime Context
  本轮入口、session、workspace、当前选择、发现策略。

Selected Data Model Reference
  模型名称、reference 摘要、reference path。

Selected Measure References
  度量值名称、自然语言口径、公式 hint、reference path。

Selected / Candidate Data Assets
  资产 ID、文件/sheet/数据库表、行列数、关键字段、profile path。

Tool Policy
  pandas_knowledge_query / database_knowledge_query / Vanna / llamaindex / web 的优先级和禁用边界。

Clarification Policy
  什么时候继续自动分析，什么时候反问用户。
```

示例 API：

```json
{
  "question": "看一下第 45 周和第 46 周比亚迪销量环比",
  "workspace_id": "optional",
  "session_id": "optional",
  "selection": {
    "model_id": "optional",
    "measure_ids": [],
    "asset_ids": [],
    "database_source_ids": []
  }
}
```

其中除了 `question`，其他字段都是可选约束。它们的处理方式是：

```text
API 参数
  -> 后端解析成 selection / session state
  -> 读取 catalog / reference / profile
  -> 拼成 prompt context
  -> 交给预编译 data_analyst
```

如果用户没有选择任何模型或资产，`data_analyst` 也可以独立运行，但必须先走发现流程：

```text
无显式 selection
  -> 检查当前 analytics session 历史
  -> 检查最近导入 / 最近上传的数据资产
  -> 检查可用数据模型和度量值
  -> 若能确定，继续分析
  -> 若不能确定，反问用户选择数据源或模型
```

#### 工具策略

问数 Agent 的工具优先级应固定：

1. `pandas_knowledge_query`：Excel / CSV / TSV 的统计、筛选、排序、分组、趋势、环比、Top N。
2. `database_knowledge_query` / Vanna：已配置数据库、多表 SQL、大数据量查询。
3. `llamaindex_knowledge_query`：只在问题明确是文档/PDF 内容理解时使用，不用于表格计算。
4. `web_search`：只在用户明确要外部实时公开数据，且本地资产无法回答时使用。
5. `glob` / `grep`：只在用户明确要定位文件或查看原始 Markdown 时使用。

这样可以避免普通 Agent 或问数 Agent 又把“比亚迪周销量环比”错误路由到 Web/RAG。

### 3.3.2 数据模型、度量值与分析模型包

在你的场景里，“模型”和“度量值”是两个东西：

```text
模型：选取哪些数据资产，以及这组数据应该如何被理解和使用
度量值：用户要看的业务指标或算法，例如配置率、快充倍率、销售额
维度：用户选择从哪个角度看，例如年份、车系、款型、区域
分析模型包：把常用模型、维度、度量值和 reference 打包，开箱即用
```

这比单纯的“语义层文档”更产品化，也更适合智能问数。关键原则是：模型和度量值优先都是可读的自然语言 reference；结构化字段、关系、公式只是为了帮助 Agent 更稳定执行，而不是让用户先做一套传统 BI 建模。

#### 数据模型

数据模型回答两个问题：

> 这次分析可以使用哪些数据？  
> 这些数据在业务上应该怎么理解？

例如：

```text
汽车配置数据模型
  数据源：
    - PostgreSQL: car_config / car_series / car_model
    - Excel: 用户临时上传的竞品清单
  reference：
    - 这些表用于分析汽车配置、车系、款型和上市年份。
    - 用户说“车型”时通常指款型；用户说“车系”时按 series_name 汇总。
    - 如果需要跨表查询，优先按 car_name / series_name 进行匹配。
```

也就是说，模型不是必须先配置主外键、事实表、维表；第一版可以只保存“选取了哪些数据资产 + 一段自然语言 reference”。只有在问数效果不稳定时，再补充关系、主键、默认时间字段等结构化提示。

#### 度量值

度量值是顶层 BI 资产，不属于某个单一 Excel，也不强绑定某个数据模型。它首先是自然语言业务口径，公式、字段、过滤条件只是可选 hint。

例如：

```text
度量值：配置率
含义：某项配置在指定对象范围内的搭载比例。
可选维度：年份、车系、款型。
计算方式：
  配置率 = 搭载该配置的对象数量 / 对象总数量
适用模型：
  - 汽车配置数据模型
  - 竞品配置对比模型
参考文档：
  references/metrics/配置率查询（款型维度）.md
  references/metrics/配置率查询（车系维度）.md
```

用户可以选择：

```text
度量值：配置率
维度：车系
时间：2022-2026
配置项：城市辅助驾驶
```

Agent 的工作是读取对应 reference，判断“车系维度”和“款型维度”的差异，然后执行多步查询。

#### 分析模型包

分析模型包是更高一层的开箱 BI 方案：

```text
汽车配置分析包
  使用数据模型：汽车配置数据模型
  内置度量值：
    - 配置率
    - 快充倍率
  推荐维度：
    - 年份
    - 车系
    - 款型
    - 品牌
  reference：
    - 配置率查询（款型维度）.md
    - 配置率查询（车系维度）.md
    - 快充速率计算.md
```

用户后续可以直接问：

```text
2023 年城市辅助驾驶配置率，按车系看
```

系统应该能够理解：

- 使用“汽车配置分析包”。
- “配置率”是度量值。
- “车系”是维度。
- “城市辅助驾驶”是度量值参数。
- “2023 年”是时间过滤。
- 需要读取配置率 reference，而不是让 Vanna 一步生成 SQL。

建议文件：

```text
knowledge/
  models/
    auto_config.model.json
    auto_config.model.md
  semantic-assets/
    measures/
      config_rate/
        measure.md
      fast_charge_rate/
        measure.md
    dimensions/
      launch_time/
        dimension.md
  packages/
    auto_config_analysis.package.json
    auto_config_analysis.package.md
```

示例 `model.json`：

```json
{
  "id": "model_auto_config",
  "name": "汽车配置数据模型",
  "description": "用于汽车配置、车系、款型相关分析的数据源集合",
  "reference": "models/auto_config.model.md",
  "sources": [
    {
      "type": "database",
      "connection_id": "local_postgres",
      "tables": ["car_config", "car_series", "car_model"],
      "role": "primary"
    }
  ],
  "dimensions": [
    {
      "id": "dim_year",
      "name": "年份",
      "description": "通常按上市日期年份统计",
      "aliases": ["上市年份", "年份"]
    },
    {
      "id": "dim_series",
      "name": "车系",
      "aliases": ["车系维度"]
    },
    {
      "id": "dim_model",
      "name": "款型",
      "aliases": ["款型维度", "车型款型"]
    }
  ],
  "relationship_policy": "reference_first",
  "relationships": [
    {
      "left": "car_config.car_name",
      "right": "car_model.car_name",
      "type": "many_to_one"
    },
    {
      "left": "car_model.series_name",
      "right": "car_series.series_name",
      "type": "many_to_one"
    }
  ],
  "default_engine": "database_knowledge_query"
}
```

说明：

- `reference` 是第一优先级，Agent 要先读它。
- `dimensions`、`relationships` 是可选的机器提示，不是强制用户一开始就配置。
- `relationship_policy=reference_first` 表示先按自然语言 reference 和 profile 理解，结构关系只用于约束和兜底。

示例 `package.json`：

```json
{
  "id": "package_auto_config_analysis",
  "name": "汽车配置分析包",
  "model_id": "model_auto_config",
  "recommended_dimensions": ["dim_year", "dim_series", "dim_model"],
  "measures": [
    {
      "id": "m_config_rate",
      "name": "配置率",
      "reference": "semantic-assets/measures/config_rate/measure.md",
      "aliases": ["搭载率", "渗透率"]
    },
    {
      "id": "m_fast_charge_rate",
      "name": "快充倍率",
      "reference": "semantic-assets/measures/fast_charge_rate/measure.md",
      "aliases": ["快充速率", "充电倍率"]
    }
  ],
  "default_engine": "database_knowledge_query"
}
```

可行性判断：

- 可行，而且应该做成智能问数的中心体验。
- 第一版不需要做完整传统 BI 建模器，只要支持“选择数据资产 + 写模型 reference + 选择度量值 + 选择维度 + 保存分析包”即可。
- 度量值是最重要的，能把“配置率/搭载率/渗透率”这类自然语言稳定映射到一个业务算法。
- 度量值可以是自然语言口径、公式 hint，也可以是多步 workflow。
- 度量值是顶层资产，可以被多个数据模型复用；复用效果不保证完美，但系统要支持。
- 维度组合可行，本质是 group by / pivot / filter，但复杂度量值需要先读对应 reference。
- 多源混合时，第一版以 Pandas 合并为主；长期稳定数据再升级到数据库/Vanna。

前端产品形态：

```text
数据模型
  -> 新建数据模型
  -> 选择数据源
       已配置数据库
       已导入 Excel/CSV
       当前会话临时 Excel/CSV
  -> 编写/生成模型 reference
  -> 选择维度
  -> 可选配置关联关系
  -> 保存

度量值
  -> 新建度量值
  -> 填自然语言口径
  -> 可选填写公式 / 字段 / 过滤提示
  -> 可选绑定 reference 文档
  -> 可选声明适用维度

分析模型包
  -> 选择数据模型
  -> 选择默认维度
  -> 选择可用度量值
  -> 绑定 reference
  -> 保存
  -> 在问数时选择该分析包
```

其中“当前会话临时 Excel/CSV”可以参与本次分析，但默认不会保存进数据模型或分析模型包。用户如果要保存，系统需要提示：

```text
该模型使用了临时文件。是否保存到知识库后再固定为数据模型？
```

这样既支持灵活分析，也避免模型引用一个会话结束后就消失的文件。

### 3.4 向量索引

向量索引主线使用 Milvus。当前 PDF 多模态 RAG 已经落在 Milvus 的 text / image 双 collection 上，本地 NL2SQL / Vanna 参考项目也使用 Milvus 保存训练向量数据。

| 后端 | 定位 | 适用 |
| --- | --- | --- |
| Milvus | 主向量索引方案 | PDF 图文混排、多模态、Vanna training data、后续高级版 |
| pgvector | 可选轻量增强 | PostgreSQL 内部的表格/profile/元数据辅助检索，不作为主向量库 |

因此，后续不是把主 RAG 从 Milvus 迁到 pgvector，而是保留 Milvus 主线；pgvector 只在确实需要“PostgreSQL 内就近做轻量检索”时作为可选能力。

## 4. Milvus 与 pgvector 的定位

### 4.1 Milvus 是高级版本主线

PuddingClaw 当前高级知识库链路已经引入 Milvus：

- PDF / Markdown 多模态 RAG：`puddingclaw_knowledge_text` + `puddingclaw_knowledge_image`。
- Vanna 训练数据：本地 NL2SQL 项目使用 `vannasql`、`vannaddl`、`vannadoc`、`vanna_entity`。
- 图片向量、文本向量、结构化训练资料都可以统一使用 Milvus 运维。

因此主线保持：

```text
高级版 / 完整知识库：Milvus
```

### 4.2 pgvector 只是 PostgreSQL 内的可选轻量增强

pgvector 的位置不是替代 Milvus，而是补 PostgreSQL 场景：

- 对 Excel / CSV profile 做轻量相似匹配。
- 对结构化数据源描述、字段说明、表说明做小规模检索。
- 对没有 Milvus 的极简部署提供 fallback，但不作为高级版默认。

适用边界：

```text
Milvus：正式知识库向量索引 / Vanna training data / 多模态索引
pgvector：PostgreSQL 内的小规模辅助检索，可选
```

结论：本项目不要把 pgvector 写成默认路线。它可以作为后续优化项，但当前架构以 Milvus 为主。

## 5. Excel / CSV / TSV：PandasQueryEngine 管道

### 5.1 为什么不默认进 RAG

Excel / CSV 的核心问题通常不是“语义相似”，而是：

- 过滤
- 排序
- 聚合
- 分组
- 统计
- 计算
- 条件查询

这类问题需要可执行计算，而不是 chunk 召回。

### 5.2 导入流程

```text
上传 Excel / CSV
  -> 保存原始文件到 knowledge/imported/YYYYMMDD/
  -> 创建 import job
  -> 创建 document catalog 记录
  -> 创建 artifact 记录
  -> 抽取 table profile
  -> 注册 table asset / sheet asset
  -> 标记 pandas_engine_ready=true
```

这条链路的“落盘与入库”要和 PDF / Markdown 保持一致：

| 阶段 | PDF / Markdown | Excel / CSV |
| --- | --- | --- |
| 文件落盘 | `/knowledge/originals`、`/knowledge/imported`、`/knowledge/assets` | `/knowledge/imported`，必要时保留 `/knowledge/originals` |
| 任务记录 | import job / parse job / vector publish job | import job / profile job |
| Catalog | document / artifact / virtual path | document / artifact / virtual path / table asset |
| 可读路径 | `/knowledge/imported/YYYYMMDD/xxx.md` | `/knowledge/imported/YYYYMMDD/xxx.xlsx` 或 `xxx.csv` |
| 查询入口 | `llamaindex_knowledge_query` | `pandas_knowledge_query` |

关键点：

- Excel / CSV 不是临时文件，也不是只在前端状态里存在；它必须进入 knowledge catalog。
- 如果来自聊天附件，默认先作为 session 临时资产；用户选择保存后复制到 knowledge，并注册为正式 document。
- profile 是派生元数据，不替代原始文件。
- PandasQueryEngine 查询时读取 catalog 中登记的 artifact，而不是让 Agent 自己读任意路径。

profile 内容：

```json
{
  "file_name": "销售订单.xlsx",
  "sheets": [
    {
      "sheet_name": "2026订单明细",
      "columns": [
        {"name": "订单号", "dtype": "string"},
        {"name": "客户", "dtype": "string"},
        {"name": "金额", "dtype": "float"},
        {"name": "日期", "dtype": "datetime"}
      ],
      "row_count": 1200,
      "preview_rows": [
        {"订单号": "A001", "客户": "阿里", "金额": 12000, "日期": "2026-01-01"}
      ]
    }
  ]
}
```

### 5.3 表选择策略

多个表格时，第一版使用轻量关键词匹配，不默认做 embedding 语义匹配：

```text
用户问题
  -> 文件名 / sheet 名 / 标题 / 列名 / 样例值
  -> 加权关键词打分
  -> 选最相关表
  -> PandasQueryEngine
```

建议权重：

| 匹配项 | 权重 |
| --- | --- |
| 列名 | 最高 |
| sheet 名 / 表标题 | 高 |
| 文件名 | 中 |
| 样例值 | 低 |

原因：

- 表格问题最关键的是找对字段。
- 列名、sheet 名通常比自然语言语义更可靠。
- 结果可解释，方便前端展示“为什么选这张表”。

后续增强可以做：

```text
关键词召回 Top 3 表
  -> profile embedding rerank
  -> 用户确认或自动选择
```

### 5.4 Pandas 工具

新增工具建议封装成和 `llamaindex_knowledge_query` 同级的 Agent tool：

```text
pandas_knowledge_query
```

定位：

- `llamaindex_knowledge_query` 负责非结构化/半结构化文档语义问答。
- `pandas_knowledge_query` 负责已入库 Excel / CSV / TSV 的表格分析。
- 两者都从 PostgreSQL catalog 找资产，都返回结构化来源引用。
- Agent 在遇到“统计、筛选、排序、分组、趋势、Top N、按条件计算”等表格分析意图时调用 `pandas_knowledge_query`。

输入：

```json
{
  "query": "统计 2026 年每个客户的销售额",
  "document_id": "optional",
  "file_hint": "optional",
  "sheet_hint": "optional"
}
```

输出：

```json
{
  "answer": "2026 年销售额最高的客户是 ...",
  "table": {
    "columns": ["客户", "销售额"],
    "rows": [...]
  },
  "source": {
    "document_id": "...",
    "file_name": "销售订单.xlsx",
    "sheet_name": "2026订单明细"
  },
  "debug": {
    "selected_by": "columns: 客户, 金额, 日期",
    "generated_code": "仅 trace/debug 展示"
  }
}
```

内部流程：

```text
pandas_knowledge_query
  -> 从 catalog 找 pandas_engine_ready 的 table assets
  -> 根据 query + file_hint + sheet_hint 做表选择
  -> 加载对应 Excel/CSV artifact
  -> 构造 DataFrame
  -> 调用 PandasQueryEngine 或受控 pandas executor
  -> 返回答案、结果表、来源、trace/debug 信息
```

安全要求：

- 只允许读取知识库或当前会话附件里的表格。
- Pandas 执行环境不能开放 `open`、`os`、`subprocess`、`import` 等危险能力。
- 默认不把生成代码暴露给普通用户，只在 trace/debug 中展示。
- 超过阈值的大表不建议 Pandas，提示转入数据库。

### 5.5 聊天附件和粘贴路径

统一入口必须覆盖：

| 输入方式 | 行为 |
| --- | --- |
| 知识库页面上传 Excel | 注册为正式 table asset |
| 聊天框上传 Excel | 注册为 session 临时 table asset |
| 粘贴本地 Excel 路径 | 后端校验白名单/授权后读取并注册 |
| 粘贴已配置 knowledge 下路径 | 直接注册或临时读取 |

临时附件规则：

```text
backend/data/attachments/{session_id}/{att_xxx}/...
```

属于托管资源，可被工具读取，但默认只在当前会话有效。用户点击“保存到知识库”后才复制到 `knowledge/imported/`。

### 5.6 Excel / CSV 与结构化数据库混合分析

这是非常常见的场景：

> 数据库里有订单、客户、商品等正式业务表；用户临时上传一个 Excel，里面是活动名单、预算、外部竞品价格、人工标注结果，希望一起分析。

例如：

```text
PostgreSQL:
  orders
  customers
  products

用户上传 Excel:
  2026Q3_重点客户名单.xlsx
  字段：客户名称、客户等级、负责人、预算额度
```

用户问：

> 重点客户名单里的客户，今年实际采购额和预算差距最大的是哪些？

默认方案不应该把这个 Excel 训练进 Vanna，也不应该默认写入正式数据库。第一阶段采用轻量临时混合：

```text
用户问题
  -> 读取 Excel/CSV profile + semantic reference
  -> 加载 Excel/CSV 为 DataFrame
  -> 根据问题生成只读 SQL 查询正式数据库
  -> SQL 结果转 DataFrame
  -> Pandas merge / join / groupby / analysis
  -> 返回答案、结果表、来源
```

示例逻辑：

```python
excel_df = read_excel("重点客户名单.xlsx")
orders_df = query_postgres("""
  SELECT customer_name, SUM(amount) AS actual_amount
  FROM orders
  WHERE order_date >= '2026-01-01'
  GROUP BY customer_name
""")

merged = excel_df.merge(orders_df, on="customer_name", how="left")
merged["gap"] = merged["budget"] - merged["actual_amount"]
```

这个方案的优点：

- 不污染 Vanna training data。
- 不污染正式数据库。
- 适合临时文件和会话附件。
- 实现成本低，和 PandasQueryEngine 自然融合。
- 用户仍然只看到一个上传入口。

边界：

| 场景 | 默认处理 |
| --- | --- |
| 只问 Excel/CSV 内部统计 | `pandas_knowledge_query` |
| 问 Excel/CSV + 数据库 | `pandas_knowledge_query` 内部调用只读 SQL，并做 DataFrame 合并 |
| 问正式业务数据库指标 | `database_knowledge_query` / Vanna |
| Excel/CSV 要长期复用、多人共享、大量 join | 用户确认后升级为数据库表 |

因此 `pandas_knowledge_query` 需要支持两种数据源：

```json
{
  "query": "重点客户里哪些预算高但成交低？",
  "table_assets": [
    {
      "type": "uploaded_table",
      "document_id": "doc_xxx",
      "sheet_name": "重点客户"
    }
  ],
  "database_refs": [
    {
      "connection_id": "local_postgres",
      "tables": ["orders", "customers"]
    }
  ]
}
```

内部策略：

1. 小数据：Excel/CSV 和 SQL 查询结果都进 DataFrame，在 Pandas 中合并。
2. 中等数据：SQL 侧先聚合，再把聚合结果拉回 Pandas 合并。
3. 大数据/长期数据：提示用户“转为数据库表”，再走 `database_knowledge_query`。

第一阶段只做 1 和 2，不默认实现“上传表写入数据库”。

如果用户希望这类混合分析长期复用，应保存成数据模型或分析模型包，而不是让 Agent 每次临时猜关联：

```text
临时混合分析
  -> 用户确认效果正确
  -> 保存为数据模型或分析模型包
  -> 临时 Excel 先保存到 knowledge/imported/
  -> 模型记录数据源、维度、度量值、关联关系
  -> 后续问数直接选择/匹配该模型
```

分析模型包保存后，问数流程变成：

```text
用户问题
  -> 选择/匹配分析模型包
  -> 读取模型度量值和维度
  -> 读取数据库 + Excel/CSV 资产
  -> Pandas 或 SQL 执行
  -> 返回答案
```

## 6. 结构化数据库：Vanna NL2SQL 管道

### 6.1 Vanna 的定位

Vanna 不替代 Pandas，也不替代 LlamaIndex RAG。

它负责：

> 针对结构化数据库，把自然语言转换成可验证、可执行、可解释的 SQL。

适合：

- 多表关联。
- 大表查询。
- 业务指标计算。
- 结构化事实库。
- 用户已有数据库。
- Excel / CSV 规模变大后导入数据库。

### 6.3 PuddingClaw 集成方式

不要把 Vanna 做成一个外部 FastAPI 服务暴露给 Agent。旧 NL2SQL 项目只作为参考实现；PuddingClaw 默认把 Vanna 封装成后端内部能力包，由统一 tool 调用：

```text
backend/
  analytics/
    nl2sql/
      service.py
      table_router.py
      vanna_client.py
      sql_runner.py
      schemas.py
      training.py
      entity_candidates.py
      improve/
        clients/
          ...
  tools/
    database_knowledge_tool.py
```

默认调用链：

```text
Agent / 问数 Agent
  -> database_knowledge_query
    -> backend.analytics.nl2sql.service
      -> table_router
      -> 将允许数据源 / 表 / 字段拼入 Vanna prompt
      -> Vanna / Milvus training data
      -> read-only SQL runner
      -> SQL + result table + explanation + references
```

边界：

- Vanna 是 PuddingClaw 问数能力包，不是独立产品服务。
- 旧 NL2SQL FastAPI 不作为默认依赖，不新增第二套路由、生命周期、配置和状态管理。
- 未来可以把旧服务做成 external provider，但默认实现必须以内嵌 backend service 为准。
- `database_knowledge_query` 是 Agent 唯一稳定入口，不能让 Agent 直接调用 Vanna client、Milvus collection 或数据库连接。

内部模块职责：

| 模块 | 职责 |
| --- | --- |
| `service.py` | 编排问数主流程：选表、召回训练资料、生成 SQL、执行、解释和返回引用 |
| `table_router.py` | 基于 catalog 和上下文选择候选数据库表，避免全库无约束猜表 |
| `vanna_client.py` | 封装本地已验证 Vanna fork / Improve clients |
| `sql_runner.py` | 只读 SQL 安全检查、超时、limit、分页和结果预览 |
| `schemas.py` | tool 输入输出、错误、引用资料和 SQL 结果结构 |
| `training.py` | DDL、业务说明、SQL 示例、Entity 训练资料写入与回看 |

Vanna adapter 第一版可以有两种落地方式：

| 方式 | 说明 | 推荐 |
| --- | --- | --- |
| embedded / vendored adapter | 把 NL2SQL 中已修复的 Vanna 源码/adapter 作为 backend 内部模块使用 | 默认推荐 |
| sidecar service | 保持 NL2SQL vanna 服务独立运行，PuddingClaw 通过 HTTP 调用 | 仅作为未来 external provider 或过渡方案 |

考虑到用户已验证本地版本，建议：

1. 默认采用 embedded / vendored adapter。
2. 沿用本地项目验证过的 Vanna、Improve clients、Milvus、embedding 适配。
3. 依赖版本固定在本地项目验证过的范围，不追 archived 上游。
4. 不启动旧 FastAPI 服务作为 PuddingClaw 默认能力。

### 6.4 Vanna 训练数据

Vanna 需要的不是 PDF chunk，而是结构化上下文：

- DDL
- information_schema
- 字段解释
- 表业务说明
- 术语表
- 问题-SQL 样例
- 实体映射
- 历史修正 SQL

重要边界：

> 临时上传的 Excel / CSV 默认不进入 Vanna 训练。

原因：

- 临时表生命周期短，进入训练库会制造过期知识。
- 上传文件经常是一次性分析材料，不应该污染长期 SQL 生成上下文。
- Vanna training data 更适合稳定 schema、稳定指标、稳定业务术语和高质量 question-SQL 样例。
- 本项目高级版已经使用 Milvus 保存 Vanna training data，训练库越干净，后续召回越稳定。

默认规则：

| 资产 | 是否默认进入 Vanna 训练 |
| --- | --- |
| 正式业务数据库 schema / DDL | 是 |
| 稳定字段说明、业务指标、术语表 | 是 |
| 用户确认沉淀的 question-SQL 样例 | 是 |
| Entity mapping / 业务实体别名 | 是 |
| 临时上传 Excel / CSV | 否 |
| 聊天附件 Excel / CSV | 否 |
| 一次性分析结果 | 否 |

只有当用户明确把某个 Excel / CSV 标记为“长期数据表”时，才进入数据库化与 Vanna 训练流程：

```text
Excel / CSV
  -> 用户确认“保存为长期数据表”
  -> 导入 PostgreSQL / DuckDB
  -> 生成 DDL / schema profile
  -> 写入 semantic reference
  -> 可选训练 Vanna
  -> 后续走 database_knowledge_query
```

训练流程：

```text
连接数据库
  -> 抽 schema / DDL
  -> 生成训练计划
  -> 写入 vannaddl / vannadoc
  -> 可选写入 question-sql pairs
  -> 可选构建 entity mapping
```

### 6.5 SQL 查询流程

```text
用户问题
  -> database_knowledge_query
  -> table_router 选择候选数据源 / 表
  -> Vanna 召回 DDL / doc / similar SQL / entity
  -> 生成 SQL
  -> SQL 安全检查
  -> 只读执行
  -> 返回表格结果 + SQL + 来源
```

### 6.5.1 后端表 Router

表 Router 是 `database_knowledge_query` 的内部步骤，不是独立 Agent。它解决的是“这次问题应该把哪些表交给 Vanna”，而不是替代 Vanna 写 SQL。

输入来源按优先级：

1. 用户或 UI 显式选择的 `database_source_id` / `table_names`。
2. 当前问数工作台上下文里的数据源、数据模型、度量值和表。
3. 数据模型 reference / 度量值 reference 中声明或提到的数据源、表、字段和业务对象。
4. 数据资产 catalog 中的表名、字段名、profile 摘要、业务说明、训练资料统计。
5. 用户问题本身的关键词和业务实体。

输出示例：

```json
{
  "database_source_id": "dbs_xxx",
  "candidate_tables": ["vehicle_params"],
  "reason": "问题命中 vehicle_params 的车型/配置字段，并且当前上下文选择了 insight_data 数据源",
  "confidence": 0.86,
  "needs_clarification": false
}
```

关键规则：

- Router 只做候选表收敛，Vanna 仍负责根据训练资料生成 SQL。
- Router 的输出会被 `service.py` 拼入 Vanna prompt，明确告诉 Vanna 当前允许的数据源、数据表和字段。
- Prompt 约束不是唯一安全边界；Vanna 生成 SQL 后，`sql_runner.py` 必须再次解析 SQL 引用表，并确认只访问 Router 输出的允许表集合。
- Router 必须白盒化：`table_router.py` 写后端开发态日志，前端 Trace 面板能看到选中的表、候选表、评分和决策原因；但 `database_knowledge_query` 返回给 LLM 的正文只保留数据源、表、SQL 和结果摘要，避免把调试明细全部塞进模型上下文。
- 如果 UI 已明确选择表，Router 不应再绕开用户选择。
- 如果候选表冲突或置信度不足，返回澄清问题，不直接执行。
- SQL 执行前必须校验 SQL 引用表属于 Router 允许集合。
- 表选择依据优先来自 PuddingClaw 数据资产 catalog；Vanna training data 作为补充上下文，不作为唯一 catalog。
- 第一版可以先做关键词 / 字段 / reference 加权召回；后续表很多时，再用 pgvector 或 Milvus 做 profile rerank。

### 6.5.2 `database_knowledge_query` 输出与 Trace 边界

`database_knowledge_query` 有两个不同受众：

1. LLM：只需要足够回答用户问题的业务结果。
2. 开发者 / 用户调试：需要看到 SQL 是如何生成的。

因此工具输出必须分层：

| 输出位置 | 内容 |
| --- | --- |
| LLM tool output | 数据源、表、SQL、结果行数、必要的结果预览 |
| Trace: `database.router` | Router 选择的数据源、候选表、选中表、字段预览、置信度和原因 |
| Trace: `database.vanna_references` | Vanna 召回的 DDL、业务说明、SQL 示例 |
| Trace: `database.vanna_entities` | Vanna 实体召回分数，按 `entity_type` 分组，每组 Top-10，同时保留全局预览 |
| Trace: `database.sql_generation` | 最终生成的 SQL、生成来源、允许表 |
| Trace: `database.sql_execution` | 执行列、总行数、是否截断、结果预览 |

关键规则：

- Vanna 实体不能只做全局排序后直接喂给 SQL 生成；必须先按实体类型召回与排序。
- 每个实体类型默认进入 prompt 的实体数为 Top-10；可通过 `vanna.query.entity_top_k_default` 和 `vanna.query.entity_top_k_by_type` 按项目或实体类型调整。
- `entity_type` 来自当前 Router 选中表已有的实体训练数据。
- LLM 不直接看到 Router / Vanna / Entity 的完整调试 JSON；这些内容只进入 Trace。
- Entity 召回逻辑不能拆成两套：`database_knowledge_query` 预先调用 Vanna 的 `get_related_entities()` 生成 Trace 和分组 TopK，然后把同一份 `entity_list` 传给 `VannaBase.generate_sql()`；Vanna 收到 `entity_list` 时跳过内部二次召回。只有没有传入预召回实体的独立 Vanna 调用，才使用 Vanna 原始的 `get_related_entities()` 兜底。

安全边界：

- 第一版只允许 `SELECT`。
- 禁止 `DROP`、`DELETE`、`UPDATE`、`INSERT`、`ALTER`、`TRUNCATE`。
- 强制 limit。
- 超时控制。
- 大结果分页。
- SQL 展示给用户确认可作为可选开关；默认可以执行只读查询。

### 6.6 Excel / CSV 升级到结构化数据库

当 Excel / CSV 满足以下条件时，不建议继续 Pandas：

- 行数超过阈值，例如 10 万行。
- 多文件/多表需要 join。
- 用户需要长期反复分析。
- 需要增量更新。
- 需要多人共享。

升级流程：

```text
Excel / CSV
  -> 用户确认“转为数据库表”
  -> 导入 PostgreSQL 或 DuckDB
  -> 生成表 schema
  -> 生成 semantic reference
  -> 可选训练 Vanna
  -> 后续走 database_knowledge_query
```

注意：这里必须是用户主动确认，不能因为上传了一个文件就自动训练 Vanna。

### 8.1 推荐工具

| 工具 | 使用场景 |

- Vanna 生成的 SQL 必须经过安全检查。

```text
  数据资产 Catalog
    - 同步知识库里已导入的 Excel/CSV/TSV
    - 生成 / 刷新 profile.json
    - 查看字段、行数、sheet、采样和 profile 状态

  数据模型
    - 新建数据模型
    - 选择数据库连接
    - 选择已导入 Excel/CSV
    - 配置可用维度
    - 可选配置表关系

  度量值
    - 新建度量值
    - 填自然语言口径
    - 可选绑定公式 hint
    - 可选绑定 reference 文档
    - 可选声明适用维度

  分析模型包
    - 选择数据模型
    - 选择默认维度
    - 选择可用度量值
    - 绑定 reference
    - 保存为开箱即用的问数组合
```

知识库页面和聊天问数入口可以链接到这里。

问数时支持三种数据范围：

| 范围 | 含义 |
| --- | --- |
| 分析模型包 | 推荐，最稳定；使用已保存的数据模型、维度、度量值和 reference |
| 数据模型 | 固定数据资产和模型 reference，用户临时选择度量值与维度；关系只是可选提示 |
| 已导入资产 | 从知识库里选择一个或多个 Excel/CSV 临时分析 |
| 会话临时文件 | 只在当前对话有效，可参与分析，但保存成数据模型/分析包前必须先保存到知识库 |

用户体验：

```text
问数输入框
  数据范围：
    - 自动选择
    - 选择分析模型包
    - 选择数据模型
    - 选择已导入表格
    - 使用当前会话附件
```

默认策略：

- 如果用户选了分析模型包，就严格按包里的数据源、度量值、维度和 reference 问数。
- 如果用户只选了数据模型，就让用户/Agent 再选择度量值和维度。
- 如果用户没选，系统可以按问题匹配分析模型包或数据模型。
- 如果问题引用了刚上传的 Excel，就优先用当前会话附件。
- 如果用户要把当前分析保存成数据模型或分析模型包，临时附件必须先落盘到 knowledge。

## 13. 最终原则

1. 入口统一，pipeline 分流。
2. 文档走 RAG，表格走计算，数据库走 SQL。
3. PostgreSQL 管记录和结构化事实，不塞真实文件。
4. Milvus 是主向量索引和 Vanna training data 后端；pgvector 只是 PostgreSQL 内部可选辅助检索。
5. Vanna 只服务结构化数据库，不混进普通 PDF RAG。
6. Excel/CSV 默认先 Pandas；临时文件不进 Vanna，不写正式库。
7. Excel/CSV + 数据库混合分析第一版走 Pandas 临时合并，只有长期数据表才升级数据库 + 可选 Vanna。
8. 智能问数要支持三层抽象：数据模型、度量值、分析模型包。
9. 数据模型/分析模型包不能引用会话临时文件；临时文件要保存到知识库后才能进入模型或分析包。
10. 数据语义层是数据版 Skill reference，Agent 查数据前必须先读 package / model / measure / profile / reference。
11. Agent 看到的是清晰工具，不是让模型自由猜 pipeline。
12. Vanna 依赖沿用本地已验证版本，不追 archived 上游。
