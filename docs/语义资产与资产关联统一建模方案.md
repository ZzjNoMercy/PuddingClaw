# 语义资产与资产关联统一建模方案

> 状态：待审核  
> 范围：智能问数工作台中的维度、实体解析、资产关联、分析模型上下文与前端维护。  
> 本文是设计稿，不代表当前功能已经全部实现。

## 1. 目标与结论

目标不是把 PuddingClaw 做成需要人工预先维护全部关系的传统 BI 工具，而是让用户定义业务边界、让 AI 批量发现和维护映射、让已确认结果可复算且可迁移。

统一结论：

1. 上市时间、价格段、车系、品牌、自然周、自然月在用户视角都叫**维度**；它们都可以筛选、分组、排序和钻取。
2. 差异不再体现在前端一级分类，而体现在维度的 `resolution_mode`，即该维度怎样从数据资产得到值。
3. 资产关联是独立的语义资产。它既支持“事实表 -> 维度”的绑定，也支持“事实表 <-> 事实表”的直接或经由维度的联合分析。
4. 分析模型不拥有一份私有关系副本，而是选择工作区内已发布的维度、资产关联、度量值、颗粒度与 SQL 守卫；同一关联可被多个模型复用。
5. `entity_lookup` 是一种维度创建方式。它允许用户在前端选择来源字段，由 AI 发现和批量匹配剩余原始值，用户只审核少数不确定项。

## 2. 概念边界

| 概念 | 解决的问题 | 例子 |
| --- | --- | --- |
| 数据资产 | 数据在哪里、有哪些字段 | 上险量 Excel、`vehicle_params_wide` |
| 度量值 | 怎么计算一个指标 | 销量、配置率、充电倍率 |
| 维度 | 怎样筛选、分组、标准化表达业务对象 | 车系、价格段、自然周、能源类型 |
| 颗粒度 | 统计对象如何去重或汇总 | 款型、车系 |
| 资产关联 | 多个数据资产如何在一次分析中共同使用 | 上险量表与配置表通过车系联合；订单与库存按日期、仓库、SKU 联合 |
| 分析模型 | 某类分析任务应该选择哪些资产、规则和输出模板 | 汽车行业综合分析 |

### 2.1 不再拆分“逻辑维度”和“共享维度”

用户只看到“维度”。系统用 `resolution_mode` 区分实现：

| `resolution_mode` | 示例 | 底层行为 |
| --- | --- | --- |
| `source_field` | 能源类型、车型级别 | 直接读取一个已确认的来源字段 |
| `derived` | 价格段、上市年份 | 按字段和业务规则计算 |
| `entity_lookup` | 车系、品牌、经销商 | 原始来源键映射到规范 `entity_key` |
| `calendar_lookup` | 自然日、自然周、自然月、周第一天 | 日期字段映射到日历成员及其周期属性 |

`车系`和`价格段`在分析语义上完全平等：都能筛选、分组和出现在结果中；区别只在系统如何取得维度值。

## 3. 文件与资产结构

所有内容归入 `semantic-assets/`，避免把“业务实体”和“资产关联”做成用户认知上的顶级孤岛。

```text
backend/semantic-assets/
  measures/
  dimensions/
    launch_time/
      dimension.md
    price_band/
      dimension.md
    vehicle_series/
      dimension.md
      entities.jsonl
      bindings/
        insurance_sales.jsonl
        vehicle_config.jsonl
    calendar/
      dimension.md
      calendar.jsonl or calendar.sql
  grains/
  relations/
    insurance_sales_to_vehicle_series/
      relation.md
    vehicle_config_to_vehicle_series/
      relation.md
    insurance_sales_to_calendar/
      relation.md
    insurance_sales_to_vehicle_config/
      relation.md
```

`dimensions/vehicle_series` 是可复用的车系规范中心；它不规定哪两张事实表一定要联合。`relations/` 才规定某个资产在某个分析场景中怎样与维度或另一个资产发生关系。

复杂维度的构建能力由独立的 `build-semantic-dimension` Skill 提供，而不是塞进语义资产目录。Skill 基于一个或多个 `source_bindings` 清洗、归一并生成规范成员、lookup/crosswalk 或显式配置的中间维度表；`dimension.md` 仍是语义入口，负责声明输入、输出、刷新方式和审核边界。维度目录只保存说明文档和完成后的结果；Skill 不会被 Agent 自动执行。

当前 Demo 中的 `entity-resolutions/vehicle_series` 已迁移到：

```text
semantic-assets/dimensions/vehicle_series/
```

## 4. 统一维度格式

每个维度都以 `dimension.md` 为入口，文件头保留统一字段：

```yaml
formatter: semantic-asset
id: vehicle_series
name: 车系
type: dimension
version: 0.1.0
description: 用于跨来源统一识别汽车品牌与车系。
aliases: [车系, 车系名称, serial_name]
tags: [汽车, 跨源分析]

resolution_mode: entity_lookup
grain: vehicle_series
canonical:
  key: entity_key
  fields: [canonical_brand, canonical_series]
```

### 4.1 `entity_lookup` 维度

适合原始名称不一致、但需要落到同一个标准业务对象的场景。

车系维度中的规范实体：

```yaml
entity_key: 比亚迪::秦plus
canonical_brand: 比亚迪
canonical_series: 秦PLUS
status: active
```

每个数据资产单独维护来源绑定：

```yaml
source_asset:
  display_name: 2023年1-5月乘用车市场上险量.xlsx
  internal_ref: table_asset:tbl_xxx
source_key:
  品牌: 比亚迪
  1-子车型: 比亚迪秦PLUS
entity_key: 比亚迪::秦plus
status: accepted
method: series_brand_prefix_normalized_exact
confidence: 1.0
```

配置库也使用同一个 `entity_key`，但保留其自己的原始键：

```yaml
source_asset:
  display_name: insight_data · vehicle_params_wide
  internal_ref: dbs_xxx.vehicle_params_wide
source_key:
  brand: 比亚迪
  serial_name: 秦PLUS
entity_key: 比亚迪::秦plus
status: auto_matched
```

`canonical_series` 不能独立作为 Join 键。跨源联合必须使用 `entity_key`，或完整使用 `canonical_brand + canonical_series`。

### 4.2 日历维度

日历也是普通维度，只是它的 `resolution_mode` 是 `calendar_lookup`。它提供可复用的日期成员和业务周期属性：

```yaml
date_key: 20260710
calendar_date: 2026-07-10
natural_week_start: 2026-07-06
natural_week_end: 2026-07-12
month_start: 2026-07-01
year_month: 2026-07
week_start_day: monday
```

业务表可以按日、自然周、自然月等不同粒度绑定日历，但必须明确周起始日、时区和统计周期定义。

## 5. 资产关联

资产关联是一种独立语义资产，不等于数据库物理外键。它为 Agent 提供可执行的联合分析契约，并保留 Prompt 驱动的灵活性。

### 5.1 支持的关联类型

| 类型 | 适用场景 | 示例 |
| --- | --- | --- |
| `dimension_binding` | 一个数据资产连接到一个维度 | 上险量 `品牌 + 1-子车型` -> 车系；订单日期 -> 日历 |
| `direct_join` | 两个事实/业务表有明确可用的键 | 订单明细 `order_id` -> 订单主表 `order_id` |
| `via_dimension` | 两个事实表通过已选维度联合 | 上险量和产品配置通过车系；销售和库存通过日期 + SKU |
| `bridge_mapping` | 多对多、代码映射或中间表 | 门店归属、渠道映射、套装与 SKU |
| `semantic_join` | 无法完全静态化的业务关联 | AI 按关系 Playbook、候选集和审核结果完成联合 |

`semantic_join` 不是允许 LLM 任意猜测。它必须声明可用资产、候选字段、可调用的解析维度、禁止规则和最终验证要求。

第一版对 `semantic_join` 的边界是：允许 AI 在工作流中生成候选关系、解释匹配理由、估算覆盖率和列出风险；但正式分析不能直接使用未落资产、未审计的临时推断。高置信自动规则可以自动发布，低置信候选必须进入审核。运行时 Agent 只能复用已经发布的关系或维度 binding。

### 5.2 维度绑定关系示例

```yaml
formatter: asset-relation
id: insurance_sales_to_vehicle_series
name: 上险量表关联车系维度
type: dimension_binding
version: 0.1.0

fact:
  role: insurance_sales
  asset_selector:
    kind: table_asset
    required_columns: [品牌, 1-子车型, 销量]
  key_fields: [品牌, 1-子车型]

dimension:
  ref: dimension:vehicle_series
  resolution_mode: entity_lookup
  output_key: entity_key

use_statuses: [auto_matched, accepted]
```

### 5.3 事实表到事实表关系示例

```yaml
formatter: asset-relation
id: insurance_sales_to_vehicle_config
name: 上险量与产品配置联合分析
type: via_dimension
version: 0.1.0

left:
  role: insurance_sales
  asset_selector:
    kind: table_asset
    required_columns: [品牌, 1-子车型, 销量]

right:
  role: vehicle_configuration
  asset_selector:
    kind: database_table
    required_table: vehicle_params_wide
    required_columns: [brand, serial_name]

join_path:
  - relation: asset_relation:insurance_sales_to_vehicle_series
  - dimension: dimension:vehicle_series
  - relation: asset_relation:vehicle_config_to_vehicle_series

rules:
  - 只使用 join_eligible=true 的来源绑定。
  - 必须说明车系匹配覆盖率和未匹配销量。
  - 不得按原始车系名称直接跨源 Join。
```

事实到事实的关联可以是直接 Join、经由维度、经由桥表或语义 Join。系统不强迫所有问题落到星型模型，但要求每个已发布关系都有可审计的路径和适用边界。

## 6. 前端维护与 CRUD

前端一级入口保持“语义资产”，内部分类为：

```text
度量值
维度
颗粒度
资产关联
```

技术上的资产 ID（`table_asset:tbl_xxx`、`dbs_xxx`）只由后端保存，前端始终展示文件名、Sheet、数据源和表名。

### 6.1 创建 `entity_lookup` 维度

1. 用户点击“新建维度”，填写名称、描述、版本，创建方式选择“实体匹配”。
2. 选择一个或多个数据资产。系统根据 Profile 推荐品牌、车系、主键等候选字段。
3. 用户确认每个资产的字段角色，例如销量表的 `品牌 + 1-子车型`、配置表的 `brand + serial_name`。
4. AI 根据字段 Profile、规范化规则和已有实体批量生成匹配草案。
5. 用户在“映射审核”中处理少量候选、未匹配和冲突项。
6. 发布后，写入 `dimension.md`、规范实体与各资产来源绑定。

### 6.2 维度详情页

建议页签：

```text
概览 | 数据资产绑定 | 映射审核 | 规范成员 | 版本与变更
```

支持的操作：

- 新增/移除数据资产绑定。
- 修改来源字段角色。
- 接受、拒绝、手工指定或批量确认映射。
- 新建规范实体、改展示名、归档实体。
- 合并和拆分实体；这类高影响操作必须显示受影响来源绑定数。
- 查看 AI 匹配理由、置信度和原始值样例。

映射状态：

```text
auto_matched  规则高置信自动命中
accepted      用户确认
candidate     AI 候选，尚未确认
rejected      用户明确拒绝，不应重复建议
unmatched     没有候选
inactive      最新源数据中已不再出现，保留历史
```

正式分析只能使用 `auto_matched` 和 `accepted`。

### 6.3 创建和维护资产关联

用户先选关联类型，再选左右数据资产或资产角色：

- `dimension_binding`：选择一个资产、一个维度和对应字段。
- `direct_join`：选择左右资产及对应字段。
- `via_dimension`：选择左右资产和一个或多个已发布维度。
- `bridge_mapping`：选择桥接资产和字段。
- `semantic_join`：填写业务说明，AI 生成关联草案，用户审核字段、路径、验证和禁止规则。

前端显示“上险量表 -> 车系维度”，而不是 `tbl_xxx -> dbs_xxx`。

## 7. 增量更新

新增或刷新数据资产时，不全量重新让 AI 匹配：

```text
数据资产导入/刷新
  -> 读取 Profile 与来源键 distinct 集合
  -> 比对该资产已有 binding 的 source_key_hash
  -> 已存在：复用历史状态和 entity_key
  -> 新增：进入 AI 批量匹配
  -> 消失：标记 inactive，保留历史
  -> 字段结构变化：binding 标记为需要重新确认
```

每个 binding 应记录：来源资产引用、来源字段角色、原始键、标准键、状态、方法、置信度、证据、首次/最后出现时间和版本。

第一版可采用文件系统包作为可迁移源：

```text
dimension.md
entities.jsonl
bindings/<asset-binding>.jsonl
relation.md
```

后端运行时维护索引/缓存。若单个 binding 规模增长到数十万级，再引入 PostgreSQL 运行时索引表；但仍保留 JSONL 导入导出包作为迁移和审计格式。

## 8. 分析模型如何选择并注入

分析模型是工作区资产的组合器，不复制这些资产内容。

```yaml
data_assets:
  tables: [table_asset:..., dbs_...vehicle_params_wide]

semantic_assets:
  measures: [measure:config_rate, measure:sales]
  dimensions: [dimension:vehicle_series, dimension:calendar, dimension:price_band]
  grains: [grain:series]

asset_relations:
  - asset_relation:insurance_sales_to_vehicle_series
  - asset_relation:vehicle_config_to_vehicle_series
  - asset_relation:insurance_sales_to_vehicle_config
```

模型创建页新增“资产关联”选择区。用户看到名称、关联类型、左右资产、使用维度、当前覆盖率和状态；不看到内部 ID。

运行时：

1. 系统解析模型选择的数据资产、维度、关系和守卫。
2. 注入关系摘要：适用资产、字段角色、Join 路径、允许状态、覆盖率和验证要求。
3. Agent 只有在任务涉及相关资产时才读取完整 `relation.md` 与所需 binding 分片；不把全量 Crosswalk 塞进上下文。
4. 对事实表联合分析，Agent 根据关系路径规划查询；对 `semantic_join`，必须遵守关系 Playbook 并回传匹配覆盖率。
5. Trace 记录本轮命中的维度、关系、binding 版本、覆盖率、未匹配数和实际 Join 路径。

## 9. 复用范围与模型私有例外

维度和资产关联默认是 `workspace` 级共享资产，可被多个分析模型引用。这样避免多份“比亚迪秦PLUS -> 秦PLUS”逐渐不一致。

少量业务含义确实冲突的情况，例如一个模型合并 `宋PLUS DM-i/EV`、另一个模型必须拆开，应创建明确的模型私有关联或派生维度，而不能覆盖共享车系维度。

建议第一版只实现工作区共享资产；模型私有覆盖在出现真实需求后再增加。

## 10. 实施顺序

1. 扩展语义资产 Registry 与前端分类：支持统一维度和资产关联。
2. 实现 `dimension.md` 的 `resolution_mode`，先支持 `source_field`、`derived`、`entity_lookup`、`calendar_lookup`。
3. 完成 `entity_lookup` 维度的创建、绑定、审核和 JSONL 导入导出；以车系 Demo 迁移为首个实例。
4. 实现 `dimension_binding` 与 `via_dimension` 关联；先覆盖“上险量 -> 车系”“配置 -> 车系”。
5. 在模型创建页增加资产关联选择，并注入到主 Agent / 问数 Agent 上下文和 Trace。
6. 增加 `direct_join`、`bridge_mapping`、`semantic_join`，以真实多事实表案例驱动，而非一次性过度抽象。
7. 最后引入日历维度和时间绑定，明确自然周、周第一天、财年等业务配置。

## 11. 已确认的关键决策

1. 前端分类采用“度量值 / 维度 / 颗粒度 / 资产关联”四类；`entity_lookup`、日历均作为维度的创建方式。
2. 第一版允许高置信实体匹配自动发布；低置信候选进入人工审核后发布。
3. 接受 JSONL 作为第一版可迁移源格式；运行时 PostgreSQL 索引表仅在数据规模需要时引入。
4. `semantic_join` 不完全禁止 AI 参与，但禁止在正式生产分析中无审计地自由推断 Join。允许 AI 生成临时候选、解释理由和覆盖率；只有写入资产关联并经过自动高置信规则或人工审核后，才能作为正式 Join 路径复用。
5. 当前车系 Demo 迁移到 `semantic-assets/dimensions/vehicle_series/`；废弃现有 `entity-resolutions/` 临时路径。
