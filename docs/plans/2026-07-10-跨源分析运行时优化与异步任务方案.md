# 跨源分析运行时优化与异步任务方案

> 状态：实施完成。Phase 1、Phase 2、Phase 3 已完成；已通过后端回归、前端 TypeScript 校验与真实全量 Job 发布验收。  
> 关联方案：[语义维度绑定 HITL 方案](2026-07-10-semantic-dimension-hitl-binding-plan.md)  
> 复盘依据：`backend/sessions/session-50ab337bab81.json`

## 1. 目标与边界

本方案解决三类问题：

1. 让跨源分析稳定使用已发布的实体 Crosswalk，而不把完整 JSON 放入模型上下文。
2. 修复语义资产和 SQL Guardrail 的误命中，减少无关 SQL 重写与等待时间。
3. 让耗时较长的维度构建进入独立 Job，并在统一任务中心和消息中心可见。

### 1.1 规范实体基准

`vehicle_series` 以产品配置库 `vehicle_params_wide.brand + serial_name` 作为规范实体全集。Crosswalk 中每一个 `canonical_brand`、`canonical_series` 都直接来自这两个字段，来源 Excel/CSV 只会追加其原始键 binding，不能决定规范实体是否存在。

因此要区分两个集合：

- **规范实体全集**：配置库全部车系，用于配置分析和后续持续复用。
- **本次跨源可分析交集**：规范实体中已拥有 `auto_matched/accepted` 来源 binding 的子集；只有这部分 `join_eligible=true`。

未匹配和候选来源键保留为诊断记录，不会污染规范实体，也不会进入正式 Join。

不做的事情：

- 不把 Crosswalk 全量训练或注入 Vanna Prompt。
- 不要求 `KnowledgeImportJob` 与 `SemanticDimensionBuildJob` 共享同一张数据库表。
- 不让 Agent 获得任意脚本、任意路径或任意后台任务的创建权限。
- 不把“后台任务展示统一”误实现为“模型行为统一”。任务中心不改变 Agent、Skill 或模型的业务推理契约。

## 2. 本轮验证的结论

本轮以比亚迪六个车系为样本，实际完成了：

```text
读取 vehicle_series/dimension.md
  -> 读取当前 active reference: byd_chery_demo.json
  -> 验证 6 条 auto_matched + join_eligible
  -> Pandas 查询销量表
  -> SQL 查询产品配置宽表和 EAV 明细表
  -> 用同一 entity_key 汇总回答
```

匹配逻辑正确，但复盘暴露以下问题：

| 问题 | 影响 | 根因 |
| --- | --- | --- |
| 配置明细问题误触发“配置率”守卫 | SQL 生成 111.49 秒，额外重生成 22.55 秒 | 分析模型预选的 `measure:config_rate` 被当成实际命中的度量值 |
| Agent 枚举并读取了未发布的 `full_crosswalk.json` | 候选产物可能被误当活跃映射 | `dimension.md` 只写“读取 references/”，未强制只读 `reference_path` |
| EAV 字段发现和明细读取反复执行 | 多次 SQL、较长思考链 | 字段发现未收敛为结构化步骤，负向结论没有统一证据规则 |
| “未配置”表述过强 | EAV 缺失不一定等同于产品事实不存在 | 未声明字段缺失的业务含义 |

## 3. 决策一：Crosswalk 运行时按需检索 JSON

### 3.1 核心原则

`dimension.md` 是模型上下文中的语义入口；Crosswalk JSON 是确定性运行时数据。模型只需要知道“何时使用哪个维度”，不需要看到所有映射记录。

```text
模型上下文：dimension.md 的业务规则、绑定契约、active reference
运行时数据：active Crosswalk JSON 的精确索引与查找结果
```

### 3.2 活跃引用规则

实体维度只能有一个活跃 `reference_path`。涉及该维度的跨源关联时：

1. Agent 先读取 `dimension.md`。
2. 后续只允许查询 frontmatter 的 `resolution.reference_path`。
3. 不扫描同级 `references/` 目录，不读取未被引用的候选版本。
4. 用户明确提出“比较版本”“审核候选”“刷新/发布维度”时，才允许访问非活跃 reference。

`full_crosswalk.json` 在未发布前只能是 staging/candidate 产物；不得参与正式分析。

### 3.3 后端 JSON 索引

新增内部服务 `SemanticCrosswalkStore`，不新增模型可见的文件读取行为。

```text
加载输入：dimension_id + active reference_path
缓存键：resolved_path + mtime_ns + file_size
索引键：(source_ref, normalized_source_key_hash)
索引值：entity_key, canonical fields, status, join_eligible, confidence
```

`normalized_source_key_hash` 使用稳定的字段顺序和 JSON 序列化后计算；归一化规则由 Crosswalk 构建时的 source contract 决定，不能由调用方临时猜测。

缓存失效策略：

- 首次查找惰性加载 JSON。
- `mtime_ns` 或文件大小改变时重新解析。
- 新文件解析和校验通过后才原子替换缓存；解析失败继续保留上一份可用缓存，并记录错误。
- 进程重启后可重新从已发布 JSON 建索引，不依赖内存持久化。

当前 1.1MB、约千条记录的 Crosswalk 适合此方案；达到数十万条以上、需要 SQL 内 Join 或多进程高并发时，再评估 PostgreSQL 投影索引。

### 3.4 Agent 工具契约

新增受控工具，而不是让 Agent 用 `read_file` 读取全量 JSON：

```text
semantic_entity_lookup(
  dimension_id,
  source_ref,
  keys: [{field: value, ...}],
  include_non_joinable: false
)
```

返回结构：

```json
{
  "dimension_id": "vehicle_series",
  "reference_path": "references/byd_chery_demo.json",
  "reference_version": "0.1.0",
  "matched": [
    {
      "source_key": {"品牌": "比亚迪", "1-子车型": "比亚迪秦PLUS"},
      "entity_key": "比亚迪::秦plus",
      "status": "auto_matched",
      "join_eligible": true,
      "confidence": 1.0
    }
  ],
  "candidate": [],
  "unmatched": [],
  "coverage": {"requested": 1, "matched": 1, "joinable": 1}
}
```

约束：

- 默认只返回 `auto_matched/accepted + join_eligible=true`。
- `candidate` 和 `unmatched` 仅在调用方请求诊断时返回，不能进入正式统计。
- 单次批量键数限制为可配置值，默认 500；超过时以 cursor 分页。
- Trace 必须记录 `dimension_id`、`reference_path`、版本、请求数、可 Join 数和未匹配数，不记录整份 Crosswalk。

对于大 Excel，不让 Agent 逐行查找。后续增加同一服务的批处理入口：读取资产的去重来源键，批量解析后返回映射摘要和临时结果引用；Pandas 只对这份映射结果做 Join。

## 4. 决策二：收紧语义资产与 SQL Guardrail 激活条件

### 4.1 问题

分析模型选择的资产是“可用上下文”，不等于本次问题真正需要的度量值。当前明细问题因模型包包含 `measure:config_rate`，被错误应用了配置率 Guardrail。

### 4.2 激活分层

语义资产在 Trace 中区分三种来源：

| 来源 | 含义 | 能否单独触发 Guardrail |
| --- | --- | --- |
| `model_available` | 模型包允许使用 | 否 |
| `question_matched` | 名称、别名、标签或正文命中本轮问题 | 可以 |
| `explicit_requested` | 工具参数或用户明确指定 | 可以 |

SQL Guardrail 只在以下条件之一成立时启用：

1. 关联语义资产属于 `question_matched` 或 `explicit_requested`。
2. 守卫配置了独立的意图条件且本轮问题命中。

配置率守卫的意图条件：

```yaml
activation:
  semantic_assets_any: [measure:config_rate]
  intent_any: [配置率, 搭载率, 渗透率, 配备率, 占比]
  allow_explicit_asset_override: true
```

因此“列出某车型有哪些配置”“是否有空气悬架”等明细问题不会触发配置率分母和颗粒度改写；用户显式指定“按配置率口径”时仍可触发。

### 4.3 验收

- 同一模型包中同时挂载配置率和车系维度时，车系明细查询不触发配置率守卫。
- “2026 年纯电车型空气悬架配置率”仍触发配置率守卫。
- Trace 展示 Guardrail 的真实激活原因：`question_matched`、`explicit_requested` 或 `intent_any`。

## 5. 决策三：收敛 EAV 配置发现与负向结论

### 5.1 标准两步路径

扩展既有 `database_schema_inspect`，不再新增一个泛滥的工具：

```text
database_schema_inspect(mode="eav_type_names", table="vehicle_params", patterns=[...], scope_sql_or_result_ref=...)
```

流程固定为：

1. 用宽表筛出目标款型集合，保存为受控 CTE 或结果引用。
2. 对目标集合执行一次 EAV 字段发现，得到可用 `type_name`。
3. 对已确认字段执行一次按款型聚合的 EAV 明细查询，避免循环做多个类似 SQL。

字段发现不得扫描无关全库字段；只有在目标集合没有相关字段时，才允许进行受限的全库词典诊断，并在 Trace 中标记为 `fallback_dictionary_scan`。

### 5.2 负向结论规则

EAV 查询没有记录时默认输出：

```text
在当前产品配置库中，未发现目标车型的 <字段/能力> 记录。
```

只有语义资产或字段词典明确声明：

```yaml
absence_semantics: no_record_means_not_equipped
```

才允许输出“未配置/未搭载”。否则必须标记为“数据未记录”而非产品事实。

## 6. 决策四：独立维度构建 Job 与统一任务中心展示

### 6.1 后端 Job 保持独立

不复用 `KnowledgeImportJob`：

```text
SemanticDimensionBuildJob
  id, session_id, query_id, dimension_id, adapter, input_snapshot
  requested_scope, status, current_step, progress
  staging_path, published_reference_path, error_message
  created_at, started_at, finished_at

SemanticDimensionBuildEvent
  job_id, level, message, metadata, created_at
```

Worker 生命周期：

```text
queued -> load_source_profiles -> load_source_keys -> resolve_entities
-> validate -> waiting_for_publish_confirmation
```

- 使用数据库 claim，支持重试、取消和同一 `dimension_id + input_fingerprint` 去重。
- adapter 在独立 subprocess/worker 执行，不能占用聊天 SSE 或 `terminal` 时限。
- staging 结果不可直接被分析使用。
- Job 不自动发布。用户确认后，`build-semantic-dimension` Skill 引导 Agent 校验 staging 摘要，并调用 `publish_semantic_dimension_build`：该受控工具原子替换活跃 Crosswalk、更新 `dimension.md` 的发布时间，并将 Job 回写为 `published`；任一失败保留旧活跃版本。
- Agent 调用 `enqueue_semantic_dimension_build` 后立即结束本轮；后续只通过 `get_semantic_dimension_build_job` 查询同一 Job。

用户闭环：

```text
用户：“刷新所有品牌车系维度”
  -> Agent 入队并回复 Job 已开始
  -> Job 构建、校验后进入 waiting_for_publish_confirmation
  -> 右上角通知“车系维度构建已完成，等待发布”
  -> 用户点击通知回到原对话，并发送“发布这个车系维度”
  -> Agent 查询同一 Job、读取校验摘要、调用受控 publish 工具发布
```

通知的深链必须携带 `session_id`、`query_id` 和 `job_id`；前端可将“发布这个车系维度”作为可编辑的输入建议填入对话框，但不能绕过 Agent 直接发布。

### 6.2 任务中心只统一显示层

任务中心不改变现有后端行为。它将不同 Job 适配为统一 DTO：

```json
{
  "id": "dimension_build_xxx",
  "display_type": "semantic_dimension_build",
  "title": "刷新车系维度",
  "status": "running",
  "current_step": "resolve_entities",
  "progress": 62,
  "resource": {"type": "dimension", "id": "vehicle_series"},
  "created_at": "2026-07-10 16:00:00",
  "deep_link": "/analytics?tab=semantic-assets&dimension=vehicle_series"
}
```

第一期展示类型：`knowledge_import`、`table_profile`、`vanna_entity_import`、`semantic_dimension_build`。每种类型继续使用自己的 Job 表、事件和 Worker。

任务中心支持按类型、状态、资源筛选；详情展示原始事件、失败原因、重试和取消。它是控制与历史入口，不向 Agent 暴露任意通用入队工具。

## 7. 决策五：通知中心

通知是任务中心的提醒层，不是第二套任务管理页。

```text
TaskNotification
  id, category, subject_type, subject_id, title, body
  payload(session_id, query_id, job_id), read_at, created_at
```

触发条件：

| Job 事件 | 通知 | 跳转 |
| --- | --- | --- |
| `waiting_for_publish_confirmation` | “车系维度构建已完成，等待发布” | 任务详情 / 对话继续发布 |
| `published` | “车系维度已发布” | 任务详情 / 维度详情 |
| `failed` | “车系维度刷新失败” | 任务详情，展示失败阶段和重试 |
| `waiting_for_publish_confirmation` | “维度构建等待发布确认” | 审核页 |
| `validate` 发现 candidate/unmatched | “存在待审核映射” | 映射审核页 |

前端 Navbar 右侧增加 Bell 和未读数；点击打开紧凑通知面板。通知只标记已读和跳转，不在此处执行发布、重试或取消。

## 8. Trace 与可观测性

新增或补充以下 span：

| Span | 关键字段 |
| --- | --- |
| `semantic_crosswalk.lookup` | dimension, active_reference, version, requested, joinable, candidate, unmatched, cache_hit |
| `guardrail.activation` | rule_id, activated, reason, matched_assets, intent_hits |
| `eav.discovery` | target_model_count, patterns, discovered_type_names, fallback_used |
| `semantic_dimension_build` | job_id, stage, progress, staging_path, publish_status |

要求：Trace 展示充分的决策证据，但不记录完整 Crosswalk、敏感连接信息或大型原始表数据。

### 数据资产移除边界（已完成）

智能问数中的“移除数据资产”是分析工作台的解绑操作，不等同于删除原始数据：

1. 表格资产：按同一上传文件（包含全部 Sheet）一起从表格目录移除，并删除对应 Profile；知识库中的原始 Excel/CSV/TSV 保留。
2. 数据库资产：只删除智能问数保存的连接配置和已选表，不会对外部 PostgreSQL 执行删表或删数据。
3. 被移除的资产不再出现在问数、模型或维度绑定候选中。已有模型、维度或 SQL 守卫若仍引用该资产，保留为显式待修复引用，不做静默替换。
4. 真正删除知识库原始文件仍应走知识库管理入口，避免分析配置删除误伤源文件。

## 10. 审核决策

请审核以下边界后再开始开发：

1. 当前阶段采用 JSON 内存索引，不提前投影到 PostgreSQL。
2. `semantic_entity_lookup` 是唯一查询全量 Crosswalk 的 Agent 工具；`read_file` 仅用于小型人工审核或明确文件查看。
3. 配置率 Guardrail 采用“问题意图或显式请求”双条件，不因模型包预选而自动生效。
4. 维度构建 Job 独立于知识导入 Job；任务中心只做显示聚合。
5. 发布由 Skill 引导 Agent 调用受控 publish 工具，Job 不自动发布。
6. 通知中心只提醒与跳转，任务操作统一留在任务中心或维度审核页。
