# PuddingClaw 权限机制与执行边界整体方案

> 状态：Draft  
> 日期：2026-06-30  
> 关联：外部文件读取、终端命令授权、DeepAgents/LangChain、Trace/Harness 白盒化、未来 Sandbox backend

## 1. 背景与目标

用户会在对话中临时粘贴工作区外的文件路径，例如：

```text
/Users/pet/Downloads/魔镜工程AI应用最新进展.md
```

这类需求不是“给 Agent 打开整个宿主文件系统”，而是一次具体任务中的临时授权。权限机制要满足：

- 项目内文件仍由 DeepAgents `FilesystemBackend(root_dir=project_path, virtual_mode=True)` 或现有项目内文件工具处理。
- 项目外文件默认不可读，必须由用户授权后通过 PuddingClaw 控制的只读工具读取。
- 授权 UI 尽量轻，不用大弹窗打断任务；在消息流中展示授权卡片，右侧抽屉只展示 session 级有效授权。
- 权限模型可以扩展到终端命令、未来 sandbox backend、不同 harness，以及 LangChain/LangGraph 等运行时。
- Trace 能白盒记录“何时请求权限、用户如何决策、实际执行是否被允许”，让权限成为 harness 的一部分，而不是散落在工具里。

## 2. 当前系统边界

### 2.1 Agent 文件系统

Agent 模式下，DeepAgents 文件系统只应覆盖当前项目目录：

```python
FilesystemBackend(root_dir=project_path, virtual_mode=True)
```

项目外文件访问不应通过扩展 DeepAgents backend 根目录解决，也不应切到 `virtual_mode=False`。外部路径统一交给 PuddingClaw 的权限工具读取。

### 2.2 PuddingClaw 文件工具

当前 `SandboxedReadFileTool` 的语义是“项目内相对路径读取”：

- 输入是相对项目根目录的 `file_path`。
- 后端 `resolve()` 后检查路径必须仍在项目根内。
- 这个工具不应该变成项目外读取工具。

新增能力应是独立工具，例如：

```text
read_external_file
```

它只负责已授权的项目外文件读取。

### 2.3 PuddingClaw terminal

当前 `SafeTerminalTool`：

- 通过 `cwd=root_dir` 把默认工作目录放在项目根。
- 有命令黑名单。
- 通过 shell subprocess 在宿主上执行。

这意味着在当前 fs backend 模式下，terminal 不能只靠 `cwd` 视为安全边界。绝对路径、shell 展开、重定向、脚本内部行为都可能访问项目外资源。因此 terminal 权限必须单独建模，并且在 sandbox backend 引入前保持保守策略。

## 3. 核心原则

1. PuddingClaw permission 是产品级权限层，负责策略、请求、暂停、恢复、UI、session grant、撤销、审计和 trace。
2. 权限系统从工具执行的第一性原理出发：任何高风险 side effect 在执行前必须经过可观察、可解释、可恢复的 gate。
3. LangChain/LangGraph HITL 只是可选 adapter，不是权限中心；不用 HITL middleware 也能完整实现同一套权限语义。
4. 项目外文件授权优先支持两类范围：单一文件、所有外部文件。
5. 终端授权不要提供“所有命令”这种过大范围；只能给单次命令、命令族、受限项目终端等可解释范围。
6. `once` grant 是一次工具调用级别；`session` grant 在当前会话内有效并显示在右侧抽屉。
7. 所有授权都只允许声明过的 capability，例如 `read`、`write`、`terminal`、`network`、`external_path`。
8. 拒绝也是一等结果：工具应返回清晰的拒绝信息，Agent 继续对话，不进入异常态。

## 4. 权限数据模型

### 4.1 PermissionRequest

```ts
type PermissionRequest = {
  id: string;
  sessionId: string;
  queryId: string;
  runId?: string;
  toolCallId?: string;
  type: "external_file_read" | "terminal_command" | "external_file_write" | "network_access";
  requestedBy: "deepagents" | "puddingclaw_tool" | "langchain" | "sandbox_backend";
  reason: string;
  target: PermissionTarget;
  capabilities: PermissionCapability[];
  options: PermissionDecisionOption[];
  status: "pending" | "approved" | "denied" | "expired" | "cancelled";
  createdAt: string;
  resolvedAt?: string;
};
```

### 4.2 PermissionGrant

```ts
type PermissionGrant = {
  id: string;
  sessionId: string;
  sourceRequestId: string;
  type: "external_file_read" | "terminal_command" | "external_file_write" | "network_access";
  scope: "once" | "session";
  targetKind: "exact_file" | "all_external_files" | "exact_command" | "command_family" | "project_terminal";
  target: string;
  capabilities: PermissionCapability[];
  createdAt: string;
  expiresAt?: string;
  revokedAt?: string;
};
```

### 4.3 Capability

```ts
type PermissionCapability =
  | "read"
  | "write"
  | "terminal"
  | "network"
  | "external_path";
```

## 5. 外部文件读取流程

### 5.1 判定规则

```text
收到读取路径
  ↓
resolve + realpath 规范化
  ↓
路径在 project_path 内？
  ├─ 是：走项目内 read_file / DeepAgents filesystem
  └─ 否：
      ↓
      路径属于 PuddingClaw 托管资源白名单？
        ├─ 是：允许对应 PuddingClaw 工具读取
        └─ 否：进入 external_file_read permission gate
```

### 5.1.1 PuddingClaw 托管资源白名单

有些路径虽然不在当前项目工作区内，但它们不是“任意外部文件”：它们由用户在 PuddingClaw 内显式配置，或由 PuddingClaw 在当前会话中创建。因此这些路径应视为产品托管资源，不再弹外部文件授权。

当前白名单：

| 资源 | 虚拟/引用形式 | 物理路径来源 | 读取规则 |
|---|---|---|---|
| 当前项目工作区 | `/workspace/...` | 当前 project path | 使用 DeepAgents `read_file` / `glob` / `grep`，不走外部授权 |
| 用户知识库目录 | `/knowledge/...` | `knowledge.root_dir` 或 `PUDDINGCLAW_KNOWLEDGE_DIR`，默认 `backend/knowledge` | 使用 DeepAgents 文件工具或 `llamaindex_knowledge_query`，不走外部授权 |
| 知识库图片物理路径 | 绝对路径，例如 `/Users/.../knowledge/assets/.../page.png` | 用户配置的知识库根目录下 | `read_resource` 允许读取；相关图片交给 `image_analyzer` |
| 聊天附件 ID | `att_xxx` | `backend/data/attachments/{session_id}/{att_xxx}/...` | `read_resource(att_xxx)` 允许读取；图片附件交给 `image_analyzer` |
| 聊天附件物理路径 | 绝对路径，例如 `.../backend/data/attachments/.../file.png` | `attachment_store.root_dir` 下 | 视为 PuddingClaw 托管资源，不走外部授权 |

实现入口：

- `backend/graph/managed_paths.py`
  - `is_managed_resource_path(path, base_dir)`
  - 统一判断知识库目录和附件目录。
- `backend/graph/attachment_store.py`
  - `attachment_store.root_dir`
  - 当前值为 `backend/data/attachments`。
- `backend/tools/read_resource_tool.py`
  - 处理 `att_xxx`。
  - 处理知识库/附件下的图片物理路径。
- `backend/tools/read_external_file_tool.py`
  - 在进入 external grant 检查前，先允许托管资源路径。
- `backend/graph/deepagents_manager.py`
  - image analyzer 内联图片前，允许读取 workspace / knowledge / attachments 下的图片。

设计原则：

- 用户选择的知识库目录等同于授权 PuddingClaw 管理和读取该目录。
- 用户在聊天框上传/粘贴的附件等同于授权当前 session 读取该附件。
- 托管资源白名单不代表 Agent 可以遍历宿主机，只代表这些已配置/已上传资源可被对应工具读取。
- 不在白名单、也不在 workspace 的本机绝对路径，仍必须进入 `external_file_read` 授权。

### 5.2 无授权时

后端创建 `PermissionRequest`：

```json
{
  "type": "external_file_read",
  "target": {
    "kind": "exact_file",
    "path": "/Users/pet/Downloads/魔镜工程AI应用最新进展.md"
  },
  "capabilities": ["read", "external_path"]
}
```

前端在消息流里展示轻量授权卡片：

- 单次读取此文件
- 本 session 读取此文件
- 本 session 读取所有外部文件
- 拒绝

说明：

- 单次授权不进入右侧抽屉，只在 trace/audit 中记录。
- session 授权进入右侧抽屉权限卡片，并支持撤销。
- “所有外部文件”仍只代表用户后续显式给出的路径可以被读取，不代表 Agent 可以遍历宿主目录。

### 5.3 已授权时

后端匹配有效 grant：

```text
exact_file + read
  或
session all_external_files + read
```

命中后执行 `read_external_file`，输出作为 tool result 返回给 Agent。

### 5.4 安全细节

- 统一使用 `Path.resolve()` / `realpath` 做路径规范化。
- 拒绝目录读取、glob 扫描、递归遍历。
- `exact_file` grant 应保存规范化路径；必要时保存 `stat` 信息用于提示“文件可能已变化”。
- 读取内容长度仍应受工具输出上限控制。
- 文件内容进入模型上下文前应沿用现有 tool-result truncation 与引用/来源规则，避免破坏结构化输出。

## 6. 终端命令权限

终端权限要分当前 fs backend 和未来 sandbox backend 两套执行约束。

### 6.1 当前 fs backend + host subprocess

当前 terminal 在宿主执行，风险高于 `read_external_file`。策略应保守：

- 默认仅允许项目内 cwd 下的常规读写和测试命令。
- 命令中出现项目外绝对路径时，先进入 permission gate。
- 出现重定向、管道、命令替换、通配符、环境变量展开等复杂 shell 语义时，不做乐观解析；高风险命令要求单次确认或拒绝。
- 禁止提供“本 session 允许所有命令”。

建议授权选项：

- 单次执行此命令。
- 本 session 允许此命令族，例如 `npm test`、`pytest`、`git status`。
- 本 session 允许受限项目终端：只允许 cwd 为项目根，且不访问项目外路径、不联网、不执行破坏性命令。
- 拒绝。

### 6.2 未来 sandbox backend

引入 sandbox backend 后，权限层不变，但 enforcement 更强：

- terminal 在 sandbox 内执行。
- 项目目录作为工作区 mount。
- 外部文件 exact grant 以只读 bind mount 方式暴露到 sandbox，例如 `/external/<grant_id>/filename`。
- `all_external_files` grant 不直接 mount 宿主目录，只表示后续具体路径请求可自动批准，然后仍按单文件只读 mount。
- 写权限、网络权限、宿主命令执行都需要独立 capability。

这样同一套 `PermissionGrant` 可以适配两个 backend：

| 后端 | 授权语义 | 执行方式 |
|---|---|---|
| fs backend | PuddingClaw gate + host 工具保守执行 | 工具执行前检查 grant |
| sandbox backend | PuddingClaw gate + sandbox capability/mount | 按 grant 创建只读 mount 或能力开关 |

## 7. 权限 Gate 的第一性原理

权限 gate 的核心不是 middleware，而是工具执行生命周期中的一个确定性状态机：

```text
tool intent
  ↓
normalize target + capabilities
  ↓
policy evaluate
  ├─ allowed by existing grant → execute
  ├─ denied by policy → return denial result
  └─ needs user decision
        ↓
      emit PermissionRequest + trace span
        ↓
      pause tool execution
        ↓
      user decision
        ↓
      write one-time decision or session grant
        ↓
      resume / reject / edit tool execution
```

白盒化要求每一步都有结构化事件：

- 模型/工具想做什么：`tool_start` 或 tool intent span。
- gate 为什么介入：`permission.request`。
- 给了用户哪些选项：`PermissionRequest.options`。
- 用户如何选择：`permission.decision`。
- 最终是否执行：`permission.enforce`。
- session grant 是否可见、可撤销：`permission.grant` / `permission.revoke`。

这套状态机应由 PuddingClaw permission engine 实现，任何 harness 都只能接入它，而不是绕过它。

## 8. LangChain permissions 与 HITL 的关系

LangChain/LangGraph 的权限实践经常会用 Human-in-the-loop interrupt：在工具执行前暂停，外层应用给出 approve、edit、reject 等决策，再恢复运行。

它和 PuddingClaw permission 的关系应该是：

| 层级 | 职责 |
|---|---|
| PuddingClaw permission | 权限事实源；生成请求、展示 UI、存储 session grant、撤销、审计、trace、适配不同 backend |
| LangChain/LangGraph HITL | 可选暂停/恢复 adapter；把某个 LangChain tool call 接到 PuddingClaw permission engine |

可选接入架构：

```text
LangChain tool call
  ↓
LangChain adapter detects risky call
  ↓
PuddingClaw PermissionRequest
  ↓
用户在消息流授权
  ↓
PermissionGrant / one-time decision
  ↓
adapter resumes or rejects LangChain run
```

决策映射：

| PuddingClaw 决策 | LangChain HITL 决策 |
|---|---|
| 单次允许 | approve |
| session 允许此文件/命令族 | approve + 写入 PuddingClaw grant registry |
| 修改路径/命令参数 | edit |
| 拒绝 | reject 或 response |

注意：

- 不一定要用 HITL middleware；可以在 PuddingClaw 工具 wrapper、LangGraph node、pre_tool_use hook 或自定义 runnable adapter 中接入。
- LangChain HITL 解决的是“这一次工具调用怎么暂停/继续”，不是完整的权限产品层。
- session grant、右侧抽屉、撤销、跨 harness 审计，都不能只存在 LangChain runtime 内部。
- 如果使用 LangChain/LangGraph interrupt，需要 checkpointer 或等价运行态能力来支持 interrupt 后恢复。
- DeepAgents 使用进程内 `InMemorySaver` 保存当前 SSE Run 的 LangGraph interrupt/resume 运行态；用户后续对话由 Session history 重建上下文，不依赖 checkpointer 跨请求恢复。Run 成功、失败、取消或流关闭后统一删除对应的 `session_id:query_id` thread，避免运行态持续累计。

参考官方文档：

- LangChain Human-in-the-loop：`https://docs.langchain.com/oss/python/langchain/human-in-the-loop`
- LangChain Middleware：`https://docs.langchain.com/oss/python/langchain/middleware`
- LangGraph Interrupts：`https://docs.langchain.com/oss/python/langgraph/interrupts`

## 9. Trace 与 Harness 设计

Trace 可以并且应该跟踪权限。权限是 harness 之一，建议作为 `permission` mechanism 写入 trace，而不是只在工具层返回文本。

### 9.1 新增 span

```text
permission.request
permission.decision
permission.grant
permission.enforce
permission.revoke
```

### 9.2 Span metadata

```json
{
  "mechanism": "permission",
  "harness": {
    "role": "gate",
    "backend": "fs",
    "adapter": "puddingclaw"
  },
  "permission": {
    "request_id": "perm_req_...",
    "grant_id": "perm_grant_...",
    "type": "external_file_read",
    "scope": "session",
    "target_kind": "exact_file",
    "capabilities": ["read", "external_path"],
    "decision": "approved",
    "outcome": "allowed"
  }
}
```

### 9.3 SSE 事件

新增结构化事件：

```text
permission_required
permission_resolved
permission_grant_added
permission_grant_revoked
```

这些事件与现有 `tool_start`、`tool_end`、`trace_span_start`、`trace_span_end` 并行，而不是塞进 token 文本。

### 9.4 前端展示

- 消息流：展示 pending permission request card。
- 右侧抽屉：新增“权限”视图或在现有进度/来源抽屉里增加权限卡片，只展示 session grant。
- TraceViewer：在 harness/flow 视图中展示 permission span，能看到请求、决策、执行结果。

## 10. 后端落点

建议新增模块：

```text
backend/permissions/
  models.py
  registry.py
  policy.py
  events.py
  adapters/
    langchain_adapter.py
    sandbox_backend.py
```

职责：

- `models.py`：`PermissionRequest`、`PermissionGrant`、`PermissionTarget`。
- `registry.py`：session 内 grant 存储、查询、撤销、过期。
- `policy.py`：路径、命令、网络等请求的风险判定与 grant 匹配。
- `events.py`：SSE event 与 trace span 封装。
- `langchain_adapter.py`：把 LangChain/LangGraph tool call、interrupt 或 hook 转成 PuddingClaw permission request。
- `sandbox_backend.py`：把 grant 转成 sandbox capability 或只读 mount。

工具层：

```text
backend/tools/read_external_file_tool.py
backend/tools/terminal_tool.py  # 接入 PermissionGuard
```

运行层：

```text
backend/graph/deepagents_manager.py
backend/graph/trace_collector.py
backend/session_manager.py
```

建议新增或扩展：

```text
frontend/src/lib/store.tsx
frontend/src/components/permissions/PermissionRequestCard.tsx
frontend/src/components/permissions/PermissionGrantCard.tsx
frontend/src/components/permissions/PermissionPanel.tsx

```

前端状态：

```ts
type PermissionState = {
  pendingRequests: PermissionRequest[];
  sessionGrants: PermissionGrant[];

```

交互：

- 用户点击授权按钮后，前端调用 `POST /api/permissions/{request_id}/resolve`。
- 撤销 session grant 调用 `POST /api/permissions/grants/{grant_id}/revoke`。
- store 消费 `permission_*` SSE 事件，更新消息流、右侧抽屉和 trace。

## 12. 分阶段实施计划

| 阶段 | 内容 | 验收 |
|---|---|---|
| Phase 1 | 定义 permission models、registry、SSE 事件 | session grant 可写入/撤销/恢复 |
| Phase 2 | 实现 `read_external_file` + 外部路径 gate | 项目外文件触发授权；拒绝后 Agent 收到可解释结果 |
| Phase 3 | 前端消息流授权卡片 + 右侧抽屉权限卡片 | 单次授权不进抽屉，session 授权可见且可撤销 |
| Phase 4 | Trace 接入 permission spans | TraceViewer 可看到 request/decision/enforce |
| Phase 5 | terminal permission guard | 项目外绝对路径/高风险命令触发授权或拒绝 |
| Phase 6 | Run 级内存 checkpointer + LangChain adapter | LangChain tool call、hook 或 interrupt 能转成 PuddingClaw 权限卡片并在同一 SSE 流内继续/拒绝；Run 终止后释放 checkpoint thread |
| Phase 7 | sandbox backend adapter | external file grant 以只读 mount/capability 执行 |

## 13. 测试清单

- 项目内相对路径读取不触发权限。
- 项目外 exact file 单次读取成功，下一次仍需授权。
- 项目外 exact file session 授权后，同一文件不再弹授权。
- `all_external_files` session 授权后，新外部文件路径可读取，但不能遍历目录。
- 拒绝授权后，工具返回拒绝说明，Agent 不崩溃。
- 撤销 session grant 后，再次访问同一外部路径重新触发授权。
- trace 中出现 `permission.request`、`permission.decision`、`permission.enforce`。
- 当前 fs backend 下，terminal 访问项目外绝对路径必须触发权限或被拒绝。
- sandbox backend 下，外部文件只以 read-only exact file mount 暴露。
- DeepAgents 不创建或写入 `data/checkpoints/deepagents.sqlite`；trace runtime inventory 显示 `memory / active_sse_run`，且 Run 终止后对应 thread 已释放。
- LangChain adapter 的 approve/edit/reject 或等价决策能正确映射到 PuddingClaw decision。

## 14. 仍需产品确认的问题

- “本 session 读取所有外部文件”是否默认展示，还是放到二级展开里。
- terminal 命令族如何分组：按首个 executable、按脚本入口、还是按工具预设白名单。
- session grant 是否只随当前 chat session 失效，还是允许设置短 TTL。
- 右侧抽屉权限卡片是否与来源/进度共用面板，还是独立 “权限” tab。

## 15. 推荐结论

第一版先实现外部文件只读授权：

```text
exact file once
exact file session
all external files session
deny
```
